# API 设计质量

## 概述

本技能保障 API 设计的质量与一致性。API 是前后端的契约——设计质量直接决定前端开发效率与系统可维护性。本技能为**规范/参考型**：不作为独立 6 步流程入口，按需被流程技能加载。本技能要求：**接口设计服务于具体需求，契约先行于实现**（思想见 `backend-philosophy` 卡片 1）。适用于：

- **第 1-2 步（澄清与规格）**：确定 API 风格、端点设计与契约初稿
- **第 4 步（开发）**：按契约实现，不自作主张改结构
- **review-backend-arch**：作为 API 设计一致性维度的审查依据

**核心原则**：契约即文档。接口一旦发布，改动成本高——设计时多想一步，实现后少改一次。

## 契约先行（docs/api-contracts/）

- 规格阶段产出契约初稿并落盘 `docs/api-contracts/`：初稿字段/结构即契约基线，前端按此 Mock；**定稿权归结合人员**
- 契约文档包含：端点（方法/路径）、请求/响应示例、错误码、认证方式、分页/过滤约定
- **契约变更 = 破坏性变更**：走评审，评估前端 Mock 与既有调用方影响，同步更新文档

## REST 约定

- 资源命名：复数名词（`/users`、`/orders/{id}`），不用动词；子资源表达层级（`/users/{id}/orders`）
- 动词语义：GET 读 / POST 创建（非幂等）/ PUT 全量替换（幂等）/ PATCH 局部更新 / DELETE 删除
- 状态码语义准确：200/201/204、400（客户端错误）、401（未认证）、403（未授权）、404、409（冲突）、422（校验失败）、429（限流）、500/502/503（服务端）
- URL 风格统一（kebab-case 或 camelCase 二选一，项目内固定）；查询参数与路径参数职责分明
- 响应包装格式项目内统一（直接返回资源 vs `{data: ...}` 包装，二选一不混用）

## 统一错误结构（必查）

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "邮箱格式不正确",
    "details": [{ "field": "email", "reason": "invalid_format" }],
    "requestId": "req_abc123"
  }
}
```

- 全局统一错误结构（code/message/details/requestId），**不泄露实现细节**（堆栈、SQL、内部路径）
- `code` 是机器可读错误码，前端据此分支处理；`message` 面向用户可读；`details` 给字段级校验信息
- 错误处理走集中式路径（`backend-philosophy` 卡片 2），不在各路由手写

## 分页

- 无限集合必须分页（列表接口默认分页，无上限例外）
- 方案二选一（项目内统一）：**游标分页**（大数据量、动态数据推荐，稳定排序）或**偏移分页**（offset/limit，简单场景）
- 响应含分页元数据：`{ "items": [...], "pagination": { "cursor": "...", "hasMore": true } }`
- 排序、过滤用查询参数（`?sort=-created_at&status=active`），过滤条件白名单化（防未预期参数）

## 幂等

- **写操作默认考虑幂等**（思想卡片 4）：创建类操作支持 `Idempotency-Key` 请求头，服务端按 key 去重
- 幂等实现：唯一约束兜底（数据库层）+ 请求日志按 key 查重 + 相同 key 返回首次结果
- 重试安全：客户端超时重试不产生重复副作用；回调/事件消费端去重
- 文档中标注每个写端点的幂等性（是否支持 Idempotency-Key）

## 版本化与兼容性

- 破坏性变更走版本化（URL 版本 `/v2/users` 或请求头版本），新旧并存过渡
- **向后兼容规则**：只加不改不删（新增可选字段 OK；改字段类型/改名/删字段 = 破坏性）
- 弃用（deprecation）流程：标注弃用 → 过渡期（至少一个版本周期）→ 移除；响应头 `Deprecation` 提示
- 契约变更影响面：前端 Mock、既有客户端、文档（`docs/api-contracts/`）三处同步

## 限流与资源保护

- 面向公众的 API 必须限流（防滥用与资源耗尽，OWASP API4）：`RateLimit` 响应头 + 429 + 重试时间
- 登录/认证端点限流更严（防暴力破解）
- 大响应限制：请求体大小限制、列表长度上限、超时设置（防资源耗尽）

## 认证与授权模式

- 认证方案（Bearer JWT / OAuth2 / 会话）项目内统一，令牌有过期与刷新机制（JWT 必须设 `exp`）
- 授权：对象级授权（BOLA）与功能级授权（BFLA）都要校验——不能只看登录与否（OWASP API1/API5）
- 敏感操作（删除、转账、改权限）考虑二次确认/重认证
- 安全细节见 `security-audit` 后端安全专项

## 文档与示例

- `docs/backend/` 提供每个端点的：请求/响应示例（真实形态，非占位）、错误码清单、认证说明
- 契约与示例保持一致：示例即测试断言依据（`testing-backend` 契约测试）

## 常见借口

| 借口 | 现实 |
|------|------|
| "先写代码，接口结构随手定" | 契约先行。接口是前后端信任源，随手定 = 前端返工。 |
| "错误响应不用统一" | 前端要靠 code 分支处理。不统一的错误结构让前端每个调用方各写一套。 |
| "列表不用分页，数据量不大" | 数据量会涨。分页是默认，不分页是例外（且要说明）。 |
| "破坏性变更直接改，反正没几个人用" | 前端 Mock、既有客户端全受影响。版本化 + 弃用过渡。 |
| "这个接口要不要幂等以后再说" | 幂等是写接口的设计决策，不是补丁。 |
