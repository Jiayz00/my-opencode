# 后端开发工作流（6 步）

## 角色定位（非协商）

- **只做后端**：API、数据库、业务逻辑、校验、认证。不写前端代码
- **契约产出**：规格阶段产出 API 契约初稿到 `docs/api-contracts/`（初稿字段/结构即契约基线，前端按此 Mock；**定稿权归结合人员**）；契约变更须同步更新
- **文档交付**：`docs/backend/` 后端文档（API 端点、请求/响应、错误码、数据库 schema、环境配置）
- **GitHub**：只提交 PR（base = `develop`），**不合并**任何 PR，合并由结合人员处理

```
第 1 步 需求澄清 ──→ 第 2 步 规格与计划（含契约初稿）──→ 第 3 步 权限门禁
                                                        │
                      ┌─────────────────────────────────┘ 同意
                      ▼
               第 4 步 开发与评审 ──→ 第 5 步 验收（测试套件）──→ 第 6 步 兼容性（后端回归）
                      │  ▲                                        │  ▲
                      └──┘ 问题 → 返回处理（第 1/2/4 步，见回环规则）   └──┘ 问题 → 返回处理
```

## 流程

### 第 1 步 — 需求澄清

用 `question` 确认，一次一个问题，不假设：

- API 风格（REST/GraphQL/gRPC 等）
- 需要的数据模型变更、认证/授权需求、性能需求
- 需要遵循的现有模式；前端对该功能的调用场景（影响契约设计）

**退出条件：** 需求已确认。

### 第 2 步 — 规格与计划

规格文档必须包含：

- API 端点（方法、路径、请求/响应结构）、数据模型 / schema 变更
- 业务逻辑流程、错误处理策略（错误码、错误消息格式）、校验规则
- **API 契约初稿**（写入 `docs/api-contracts/`）
- 后端文档清单（`docs/backend/`）

**多角色评审**（评审规格/计划，回答"本次修改会不会影响已有的功能？"）：

- 派发子代理：**后端架构师**（review-backend-arch）+ **QA**（review-qa）+ **安全工程师**（security-audit）+ **DevOps**（review-devops，涉及部署/环境时）
- **思想评审**：规格是否违背工程思想（契约先行/过度设计/过早抽象/范围蔓延）？可加载 `backend-philosophy` 校验（YAGNI、抽象成本、幂等、集中式错误处理）
- 汇总发现 → 交叉复核 → 修正后复核 → 更新规格

**退出条件：** 规格已评审、无冲突并保存，契约初稿已落盘。

### 第 3 步 — 权限门禁

`question`："我将通过修改 [文件] 并采用 [方案] 实现 [X]。我可以开始吗？"**未经明确许可不得编写代码。**用户拒绝 → 回到第 1 步澄清需求或停止，不擅自推进。

### 第 4 步 — 开发与评审

- 契约优先：先定义 API 结构（同步 `docs/api-contracts/`），再实现；按 `api-design-backend` 规范设计端点/错误结构/分页/幂等
- 添加错误处理和输入校验（集中式错误路径，区分操作型/程序型错误）；实现的同时编写测试（按 `testing-backend` 策略）
- 数据层变更遵守 `database-change` 流程（回滚脚本先行）
- **vibe coding 平衡**（本角色是 AI 协作开发，思想见 `backend-philosophy`）：
  - 意图先于代码：规格/契约/约束已定，AI 填实现
  - **理解优先于信任**：AI 生成的代码逐段 review，不能解释的代码不允许留下
  - 品味决策（契约设计/抽象边界/错误策略判断）由人定，不交给 AI 默认值
  - 小步迭代：一次交付一个可验证的增量
  - AI 做机械活：样板代码、重复测试、codemod 交给 AI
- **工程化门禁**：lint/format 零错误、类型检查通过、契约与实现一致（schema 校验）、错误处理统一路径、无 `any` 逃避类型（详见 feature-dev-backend 第 4 步）
- **代码评审**：按改动规模分级派发子代理（同第 2 步角色集；纯文档/单行改动自评即可）
- **验证**：运行测试套件 / lint / 构建，确认代码可用
- 发现问题：小修直接改；需调整方案返回第 2 步

**退出条件：** 代码通过评审与验证，无未解决问题。

### 第 5 步 — 验收（后端专用路径）

1. 运行完整测试套件
2. 验证 API 响应与规格/契约一致；错误场景返回正确的状态码；认证/授权正常
3. 编写/更新 `docs/backend/` 文档
4. `question` 向用户报告：实现了什么、API 摘要、如何验证
5. 用户反馈问题 → 判断问题级别：小修返回第 4 步；方案问题返回第 2 步；需求变更返回第 1 步；用户接受 → 第 6 步
6. 用户验收通过后，用 `/pr` 提交 PR（base = `develop`），**不合并**

### 第 6 步 — 兼容性测试（后端回归）

- 门禁：`question` 请求许可
- 范围：现有 API/路由仍可用、向后兼容（契约变更时）、数据无损坏
- **前端联调与全栈回归由结合人员在其流程中执行，本阶段不重复**
- 发现问题：汇总返回第 2 步；通过：报告结果，交付 PR 给结合人员处理

## 回环规则

| 情况 | 返回至 |
|------|--------|
| 需求变更 | 第 1 步 |
| 规格评审发现问题 | 第 2 步 |
| 代码评审/验证发现问题 | 第 4 步（小修）或第 2 步（改方案） |
| 验收失败（小修） | 第 4 步 |
| 验收失败（方案问题） | 第 2 步 |
| 兼容性失败 | 第 2 步 |
| 跨角色改动（契约/数据模型影响前端） | 第 2 步（契约定稿权归结合人员，转交处理） |

## 常见借口

| 借口 | 现实 |
|------|------|
| "先写代码，契约文档之后补" | 契约是前端 Mock 的依据，必须先行产出并同步 `docs/api-contracts/`。 |
| "前端页面我也顺手做了" | 越界。退回前端开发，你只管后端。 |
| "我直接合并到 main 更快" | 禁止。只提交 PR 到 develop，合并由结合人员处理。 |

## 验证清单

- [ ] 所有端点返回正确的状态码，输入校验拦截非法数据
- [ ] 认证/授权在预期位置强制实施
- [ ] 错误响应与现有模式一致
- [ ] API 契约已更新到 `docs/api-contracts/`，后端文档已交付 `docs/backend/`
- [ ] 测试套件全部通过
- [ ] 后端回归通过（第 6 步），现有行为未破坏
- [ ] 脱敏扫描通过（git-workflow 脱敏表），无凭据入仓库
- [ ] PR 已提交到 develop（未合并、未直接推送 develop/main）
