# 后端测试策略

## 概述

本技能定义后端测试的分层策略与方法。用于第 4 步开发时配套写测试、第 5 步验收时执行测试、review-qa 评审时作为测试方案依据。本技能为**规范/参考型**：不作为独立 6 步流程入口，按需被流程技能加载。

**核心原则**（Testing Best Practices）：设计**瘦测试**——测试数量少而价值高；测行为不测实现；测试是文档（用例名即规格说明）。

## 测试思想（黄金法则）

- **测试用例命名三部分**：`被测单元 + 场景 + 预期`（如 "创建订单，库存不足时，返回 422 且不扣库存"）
- **AAA 模式**：Arrange（准备数据）→ Act（执行被测行为）→ Assert（断言结果），三段分离，拒绝"一大坨"
- **黑盒测试**：只测 public 接口（API 端点、公开函数），不测内部方法——内部是实现的奴隶
- **用产品语言断言**：断言行为结果而非内部调用（"订单创建成功且库存减一"，不是"createOrder 被调用"）
- **不 catch 错误，expect 它们**：断言抛出/响应错误，不用 try-catch 包住再断言
- **fixture 局部化**：每个测试用自己创建的数据集，不依赖全局共享 fixture/seeds（测试间独立，顺序无关）
- **真实数据优先**：不用 `foo`/`bar` 占位，用贴近真实场景的数据；边界值、超长文本、特殊字符
- **测试替身选对类型**：优先真实依赖（内存数据库）> fake > stub > spy；mock 只在必须隔离时才用（见下）

## 测试金字塔（后端版）

```
        E2E（少）          API 全链路：真实 HTTP + 真实 DB + 外部依赖替身
      契约测试（中）        前端与后端的契约一致性（Pact）
     集成测试（中）        路由 + 服务 + 数据库/缓存真实协作
    单元测试（少而精）      纯业务逻辑：计算、校验、状态转换（无 IO）
```

| 层 | 测什么 | 工具 |
|----|--------|------|
| 单元 | 业务逻辑、校验规则、状态计算（无 IO 依赖） | Vitest/Jest、mocha |
| 集成 | 路由+服务+数据库/缓存协作、认证/授权、错误路径 | 测试容器（Testcontainers）+ supertest |
| 契约 | 前端期望 vs 后端实现的字段一致性 | Pact（消费者驱动）或 OpenAPI schema 校验 |
| E2E | 关键用户旅程的 API 全链路（含真实中间件） | Playwright API / k6 / 自定义脚本 |

- 分层分配按风险：核心路径（支付、认证、数据写入）重覆盖；纯透传层轻覆盖
- 集成测试用真实数据库（测试容器），**不用 mock 数据库**——mock 数据库测不出真实 SQL 问题

## Mock 策略（后端）

- **不 mock 的**：自己代码库的内部依赖（同进程内函数）、ORM、业务库——这些用真实实现
- **必须替身的**：外部边界——第三方 HTTP API（mock 网络层）、时间、UUID 生成、文件系统
- 第三方服务测试优先用契约 mock（录制真实响应）或测试环境端点，而非手工 stub
- 数据库/队列/缓存用测试容器（Testcontainers），保证测试真实且可重复
- **绝不 mock 你要断言的逻辑本身**（mock 掉校验逻辑去测"校验通过"——测了个寂寞）

## 契约测试（后端视角）

- 后端是契约的提供方：`docs/api-contracts/` 契约 → 实现 → 测试三方对齐
- **Schema 校验测试**：响应体用 OpenAPI/JSON Schema 校验（运行时 + 测试双重），结构漂移立即失败
- **消费者驱动（Pact）**：前端期望的请求/响应录制为契约文件，CI 中后端跑契约测试验证满足前端期望
- 契约不一致时记录差异，交结合人员协调——**不擅自改契约迁就测试**

## 错误流测试（必测）

- 每个端点的错误路径与成功路径同等覆盖：校验失败（400/422）、未认证（401）、未授权（403）、不存在（404）、冲突（409）、限流（429）
- **操作型错误模拟**：外部依赖超时/离线/返回畸形数据时，接口行为正确（降级或明确 5xx，不挂死）
- 断言错误响应结构统一（error 包裹层：code/message/details/requestId，见 api-design-backend），不泄露堆栈/SQL

## 幂等与并发测试

- 写操作幂等性测试：同一请求重复执行，副作用只发生一次
- 并发测试：并发写同一资源不产生脏数据（唯一约束、事务回滚验证）
- 回调/事件消费重复投递场景：消费端去重生效

## 性能测试（第 6 步相关）

- 关键接口负载测试：基线吞吐量与 p95 延迟（autocannon/k6/artillery）
- 回归对比：优化前后、依赖升级后跑同一场景（基线见 `optimization-backend`）
- 慢查询与 N+1 检测：查询日志/ORM 分析（如 Prisma/TypeORM 日志）纳入常规检查

## 覆盖率与 CI 门禁

- 覆盖率阈值按核心模块设定（建议核心 ≥ 80%，非核心不设硬门槛但需有测试）
- 测试必须**原子、独立、可重复**：不依赖执行顺序、共享可变状态、真实外部网络
- 失败的测试是阻塞项，禁止"跳过测试提交"；`skip`/`todo` 必须有理由
- CI 门禁：lint + 类型检查 + 单元/集成测试 + 契约测试 + 性能回归对比

## 本角色边界

- 后端测试在本角色内完成：单元/集成/契约/E2E API 层
- 前端相关测试（组件/浏览器）由前端开发人员负责；**全栈联调验证由结合人员执行**，本角色不重复
- 与 review-qa 关系：review-qa 审查测试方案的覆盖与回归风险，本技能提供测试方法本身

## 验证清单

- [ ] 用例名三部分（单元+场景+预期），AAA 结构清晰
- [ ] 黑盒测试：只测 public 接口，无内部实现断言
- [ ] 数据库/缓存用真实实现（测试容器），外部 HTTP 才 mock
- [ ] fixture 局部化，测试独立可重复（任意顺序）
- [ ] 错误路径全覆盖（400/401/403/404/409/422/429），错误结构统一
- [ ] 写操作幂等性已测试，并发无脏数据
- [ ] 契约测试通过（schema 校验/消费者驱动），与 `docs/api-contracts/` 对齐
- [ ] 性能基线已建立，关键接口无回退
- [ ] 覆盖率阈值达标、无跳过测试
