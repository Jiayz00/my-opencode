# 后端工程思想

## 概述

本技能是后端开发的"为什么"层——所有流程技能（feature-dev-backend、api-design-backend、testing-backend 等）都从这里取思想。流程技能告诉你**做什么**，本技能告诉你**如何思考**。本技能为**规范/参考型**：不作为独立 6 步流程入口，按需被流程技能加载。

沉淀自社区广泛实践（Node.js Best Practices、OWASP API Security、Testing Best Practices、Goodbye Clean Code、Boring Technology、vibe coding 原意）与资深后端工程师的工程判断。

## 三层境界

| 境界 | 表现 | 特征 |
|------|------|------|
| 会用 | 接口能跑通，数据能存取 | 依赖框架 API，遇到问题查文档 |
| 用对 | 设计解决方案 | 契约先行、错误处理完整、幂等与边界主动考虑 |
| 用巧 | 权衡与品味 | 知道何时抽象、何时拒绝需求、何时接受技术债 |

**本角色要求：至少"用对"，关键决策（契约设计、错误策略、数据模型、抽象取舍）要"用巧"。**

## 12 张思想卡片

### 1. 契约即文档（Contract is the documentation）

- 主张：API 契约（`docs/api-contracts/`）先行于实现——初稿字段/结构/错误格式即契约基线，前端按此 Mock；**定稿权归结合人员**（以消费者需求为准）。契约是前后端之间唯一的信任源
- 反例：先写代码，接口文档"之后补"；前端等后端好了才能开发
- 应用：规格阶段产出契约初稿并落盘；契约变更须同步更新并评估破坏性（见 feature-dev-backend、api-design-backend）

### 2. 集中式错误处理（收口思想）

- 主张：所有错误走单一处理路径——专门的错误处理对象负责记录、上报、响应转换。不依赖各层随手 try/catch
- 反例：每个路由自己 try/catch、自己写错误响应，格式不统一，关键错误被静默吞掉
- 应用：DAL 抛错 → API 层捕获 → 集中式错误处理程序（记录 + 判定操作型/程序型 + 统一响应）；错误响应格式全局统一（见 api-design-backend）

### 3. 操作型错误 vs 程序型错误

- 主张（Node.js Best Practices）：操作型错误可预期（网络失败、校验失败、超时）——记录即可；程序型错误不可预期（bug、未定义读取）——优雅重启优于带病运行
- 反例：把所有错误一视同仁记日志；或程序型错误也硬撑继续跑（状态可能已不一致）
- 应用：错误标记 `isOperational`；生产进程退出策略按错误类型区分；fail fast

### 4. 幂等与可重试

- 主张：写操作（创建、支付、回调、消息消费）天然可重试——同一请求重复执行结果一致。重试是分布式系统的基本卫生
- 反例：客户端超时重试导致重复创建订单；回调重复投递导致重复扣款
- 应用：幂等键（Idempotency-Key）、唯一约束兜底、消费端去重（见 api-design-backend）

### 5. 事务边界与数据一致性

- 主张：写多份数据时事务边界清晰——要么全成功要么全失败；不能有"半写"状态。跨服务时用最终一致 + 补偿，但边界要显式设计
- 反例：先写用户再写订单，中间失败留下孤儿数据；没有补偿逻辑的"伪事务"
- 应用：数据库事务；跨服务用 outbox/补偿机制；迁移与 schema 变更遵守 database-change 流程

### 6. 优雅降级（Graceful Degradation）

- 主张：外部依赖（第三方 API、缓存、消息队列）不可用时，系统降级而非崩溃——返回降级结果、排队重试、熔断保护下游
- 反例：第三方 API 挂了整个接口 500；缓存挂了直接打爆数据库
- 应用：超时/重试/熔断/限流分层配置；离线时返回缓存的旧数据 + 明确标识（见 integration 技能）

### 7. 可观测性是功能

- 主张：日志、指标、追踪是系统的一部分，不是事后附加。线上事故排查依赖它，优先级与业务功能相同
- 反例：上线后才发现没有日志；关键路径无指标，出问题只能猜
- 应用：请求日志含请求 ID 贯穿链路；关键操作有指标；日志**不记录敏感数据**（见 review-backend-arch、security-audit）

### 8. 性能是功能（后端版）

- 主张：延迟与吞吐量是需求指标——p95 延迟超阈值 = 功能不达标，和"接口报错"同等级缺陷。性能问题要量化、要基线
- 反例：功能上线后才发现慢；没有基线数据，优化无从对比
- 应用：第 2 步定基线（p95 延迟、吞吐量、内存），优化前后对比（见 optimization-backend）；N+1、全表扫描是缺陷不是"小问题"

### 9. Boring Technology（无聊技术原则）

- 主张：选成熟、可预期、社区活跃的技术，不为追新而承担风险。后端技术债传播面广（数据层、依赖链），选型更需保守
- 反例：为"新潮"引入未成熟 ORM/数据库/消息队列，遇到坑只能自己修
- 应用：新依赖引入前评估（维护活跃度、bug 记录、替代方案）；依赖升级不追 latest（见 dependency-update）

### 10. 每行代码都是负债

- 主张：代码的维护成本 > 编写成本。新增代码前先问：这一行值得永远被维护吗？后端代码常驻服务，负债会持续累积
- 反例：为"万一以后用到"提前写好大段未用代码、预留无用配置项
- 应用：删除死代码、不写"防御性将来码"（YAGNI）、评审时关注新增代码量

### 11. 抽象有成本（Abstraction has a cost）

- 主张（Goodbye Clean Code 教训）：抽象会隐藏重复，也隐藏理解成本与耦合。**被抽象隐藏的重复比显式重复更危险**——因为没人敢动那个"优雅"的抽象
- 反例：两个相似服务立刻抽公共层，三个月后无人能改那层代码
- 应用：**两处重复可接受，三处重复才抽象**；抽象必须让使用点显著更简单，否则不建（服务、中间件、装饰器同理）

### 12. Make it work, make it right, make it fast

- 主张（Kent Beck）：先让它能跑，再让它正确，最后让它快。顺序不可颠倒——不要边做边过度设计
- 反例：写接口的同时顺手"优化"和"抽象"，三件事互相污染，改到一半无法验证
- 应用：第 4 步先打通主路径（能跑）→ 补错误处理与边界（正确）→ 性能问题单独任务（快）；"顺便优化"是反模式

## vibe coding 协作原则（AI 时代的工程思想）

本流程是 vibe coding（AI 生成主要代码 + 人定义意图）的工程化版本。Karpathy 的原意是"信任迭代、用描述驱动"，但**vibe 不等于盲目**：

| 原则 | 内容 |
|------|------|
| 意图先于代码 | 规格、契约、约束、验收标准由人定义；AI 填实现。说不清需求就写代码 = 盲飞 |
| AI 写码，人定边界 | 架构决策、契约字段、数据模型、错误策略由人定；实现细节交给 AI |
| 理解优先于信任 | AI 生成的代码**必须 review**——"测试过了"不等于"理解过了"。改不理解的代码 = 埋雷 |
| 小步迭代，每步验证 | 一次交付一个可验证的增量；出问题能定位到具体一步 |
| AI 做机械活 | codemod、样板代码、重复测试、文档同步——让 AI 干它们擅长的 |
| 品味不可外包 | 命名、抽象取舍、契约设计、过度设计的判断是工程师的品味，不可交给 AI 默认值 |

**落地方式**：第 3 步权限门禁时说明"意图"（做什么/为什么/边界）；第 4 步对 AI 生成代码做 review（理解 + 品味审查）；评审子代理（review-backend-arch）承担"品味审查"角色。

## AI 时代反模式（评审时重点扫）

| 反模式 | 表现 | 对策 |
|--------|------|------|
| 跳过契约直接写代码 | 接口结构随手定，前端无法 Mock | 用思想卡片 1：契约先行 |
| 错误处理缺失 | try/catch 吞错、错误响应不统一 | 用卡片 2/3：集中式 + 类型区分 |
| 幂等缺失 | 写操作可重复执行副作用 | 用卡片 4：幂等键 + 唯一约束 |
| 测试只求覆盖 | 大量 mock 内部细节的"假测试" | 用 testing-backend：黑盒 + 行为断言 |
| 防御性将来码 | "以后可能用到"的接口/配置 | YAGNI：只做需求要求的事（卡片 10） |
| 顺手优化 | 功能开发中夹带"顺便优化/重构" | 卡片 12：顺序不可颠倒 |
| 一次性代码不清理 | 原型代码混入生产、死代码残留 | 每行代码都是负债（卡片 10） |

## 验证清单

- [ ] 关键决策（契约设计/错误策略/数据模型/抽象取舍）达到"用对"以上水平
- [ ] 新抽象通过卡片 11 检验（三处重复 + 使用点显著更简单）
- [ ] 无"防御性将来码"、无死代码
- [ ] 写操作已评估幂等性
- [ ] 错误处理走集中式路径，操作型/程序型已区分
- [ ] AI 生成的代码已 review（能解释、无过度抽象）
- [ ] 功能开发未夹带"顺便优化/重构"
