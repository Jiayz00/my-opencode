# 后端迁移

## 概述

后端迁移（框架升级、ORM/数据库替换、Node/语言版本升级、消息队列切换）是高风险高价值场景。本技能遵循 6 步流程，重点在第 2 步（盘点与策略）和第 6 步（兼容性与回滚演练）。

**核心原则**：迁移不是重写。一次搬一点，每步可验证，全程可回滚。数据层迁移额外遵守事务边界与一致性（思想卡片 5）。

## 步骤调整

### 第 1 步 — 需求澄清
询问：
- 迁移什么？（框架：Express→NestJS / ORM：Sequelize→Prisma；语言/运行时：Node 版本；中间件：Redis/队列）
- 为什么迁移？（维护终止、性能、生态、团队要求）
- 目标状态是什么？（新版本的具体版本、最终架构）
- 约束？（不影响现有功能、停机时间限制、数据完整性要求、既有客户端兼容）
- 是否已有官方迁移指南/社区迁移经验？

### 第 2 步 — 规格与计划（重点）
- **现状盘点**：
  - 使用点清单：被迁移对象的所有使用处（import、API 调用、配置、中间件链）——deprecation warnings（弃用警告）是最准确的迁移清单
  - 依赖图：哪些包依赖被迁移对象（间接影响）；数据层依赖的存储格式/迁移文件
  - 测试基线：迁移前完整测试套件通过，记录基线（含契约测试）
- **迁移策略**（二选一，按场景）：
  - **渐进式（推荐）**：新旧共存（兼容层/适配层）、feature flag 切换、按模块分批迁移
  - **一次性**：仅适用于小范围/低风险（纯工具库替换）
- **并行运行方案**：
  - 新旧版本 side-by-side（双写、影子流量、兼容层）
  - feature flag：灰度迁移，随时可回退到旧路径
  - 数据层迁移：新老 schema 并存期（expand-migrate-contract 模式）
- **回滚计划**：明确回滚触发条件、回滚操作步骤（git revert 或 flag 切换或数据库回滚脚本）、回滚验证
- **工具准备**：官方 codemod、迁移 CLI、自动化迁移工具清单

### 第 3 步 — 权限门禁
呈现："迁移 [对象] → [目标]。策略：[渐进式/一次性]。并行运行：[方案]。回滚：[方案]。我可以继续吗？"

### 第 4 步 — 执行迁移
- 一次迁移一个模块/区域，**每步后跑测试 + 构建 + 类型检查**
- 优先使用 codemod 做机械性转换（减少手误），人工 review 转换结果
- 迁移与功能开发严格分离：迁移期间不改业务行为，行为差异必须记录并单独确认
- 类型迁移：类型定义随代码同步迁移，禁止用 `any` 掩盖类型差异
- 数据层迁移：schema 变更遵守 `database-change` 流程（回滚脚本先行）；迁移期间数据完整性持续验证
- 被迁移对象的新弃用点持续记录，迁移完成后清理

### 第 5 步 — 验收
- 迁移完成标志：弃用警告清零、旧 API 无残留、使用点全部切换
- 完整测试套件 + 构建通过（含契约测试）
- 数据完整性验证：迁移后数据可读可写、历史数据无损
- 行为差异清单与用户确认（无意外行为变化）
- 验收未过：行为差异未确认 → 返回第 4 步（回退该处迁移）；方案问题 → 返回第 2 步

### 第 6 步 — 兼容性 + 回滚演练（重点）
- 门禁：`question` 请求许可
- 全量回归：所有功能（不只迁移相关），重点验证迁移前后的边界行为
- 性能对比：迁移前后关键接口延迟/吞吐量对比（见 `optimization-backend`），确认无回退
- **回滚演练**：按第 2 步回滚计划实际执行一次（或至少验证回滚路径可行）——可随时回滚是迁移的安全网
- 迁移完成后清理：删除旧代码/兼容层（若确定不再需要）、在 `docs/backend/` 记录迁移决策与经验（项目级 ADR 由结合人员汇总）
- 发现问题：汇总返回第 2 步

## 特殊场景

- **官方迁移指南优先**：框架官方迁移指南、ORM 官方升级文档是权威依据，先读官方再动手
- **第三方库不可迁移**（如被迁移库本身停止维护）：评估替代库（社区活跃度、API 契合度），替代库选型需要原型验证（可加载 `prototype`）
- **数据库/中间件版本迁移**：先读官方变更说明（数据格式、协议变更）；数据层迁移遵守 `database-change` 回滚纪律

## 常见借口

| 借口 | 现实 |
|------|------|
| "一次性全切，快" | 大迁移一次切换 = 故障面全开。渐进式 + flag 才能随时回退 |
| "迁移顺便重构一下" | 迁移保行为，重构改行为。两件事分开做 |
| "旧代码以后清理" | 迁移完成后不清理 = 两套 API 长期并存。设清理里程碑 |
| "回滚不会用到" | 回滚计划是迁移的保险。没计划的迁移等于裸奔 |
| "数据层顺便一起换" | 数据层迁移独立评估（事务/一致性/回滚）。与代码迁移分开 |

## 验证清单

- [ ] 现状盘点（使用点/依赖图/测试基线）完成
- [ ] 迁移策略明确（渐进式 + flag，或一次性 + 理由）
- [ ] 并行运行与回滚计划已文档化
- [ ] 每步迁移后测试/构建/类型检查通过
- [ ] codemod 转换结果已人工复核
- [ ] 无 `any` 掩盖类型迁移
- [ ] 数据层迁移遵守 database-change 流程，数据完整性已验证
- [ ] 弃用警告清零、旧 API 无残留
- [ ] 全量回归通过，性能无回退
- [ ] 回滚演练完成（或已验证回滚路径）
- [ ] 迁移决策已记录（`docs/backend/`）
