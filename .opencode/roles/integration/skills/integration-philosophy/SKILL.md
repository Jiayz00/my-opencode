# 前后端结合哲学

## 三层境界

```
对齐 — 接口能通（Mock 已替换、请求有响应）
  ↓
一致 — 契约无差异（字段/错误/分页/鉴权全部对齐，docs/api-contracts/ 定稿）
  ↓
守护 — main 质量稳定（全栈验证 + 兼容性回归通过，团队协作顺畅）
```

- **对齐**是起点，**一致**是本职，**守护**是追求。
- 每次集成工作自问：这次交付把系统推进到了哪一层？停留在"能通"不算完成。

## 思想卡片

### 1. 契约是唯一真相

`docs/api-contracts/` 是前端、后端、结合三方共识的唯一基准：

- 前端按契约 Mock，后端按契约实现，本角色负责消除两者与契约的差异
- 契约**先于**适配代码：先对比契约，再动手改代码
- 契约变更必须同步文档——文档不同步 = 新的差异源
- 契约写的是"消费者实际需要的"，不是"后端能提供的全部"

### 2. 消费者驱动的契约（CDC）

契约由**消费者的实际使用需求**驱动，而不是由提供者单方面定义：

- 提供者契约（Provider Contract）：闭、全、单一、权威——后端实现的全貌
- 消费者契约（Consumer Contract）：开、不完整、多、非权威——前端实际使用的子集
- 消费者驱动的契约：由消费者期望推导出的提供者契约——**前端用到的才是契约**
- 含义：前端没用到的字段不是契约义务；前端用到的字段，后端变了就是破坏契约

### 3. 挖掘隐藏耦合

契约的价值不是消除耦合，而是把**隐藏耦合挖出来放到明面**：

- "前端 Mock 和后端实现各自演进"就是隐藏耦合——两边都以为自己在维护真相
- 本角色每次接口适配，都在把隐性依赖显性化
- 显性化的方式：契约文档 + 核对清单 + 契约测试。三者缺一，耦合又藏回去

### 4. 最小适配

适配只做**对齐差异**，不改业务逻辑：

- 字段映射、错误对齐、CORS/代理配置、契约补漏——这些都是适配
- 改功能、改业务规则——退回对应开发人员在自己的流程里做
- 适配代码要能删：每处 mapping/补丁都标注为什么存在（契约差异 #N）
- 越抽象越错：为"未来可能的适配"抽适配层，是过度设计

### 5. 守卫 main

main 是发布分支，本角色是它的守门人：

- 合 main 前的门禁全部真实通过：验收 + 兼容性 + 脱敏扫描 + CI
- "看起来没问题"不算通过——测试容器里跑过才算
- 守卫不是拖延：门禁是保护用户和团队，不达标的内容进 main 是欠债

### 6. 全栈验证

单一领域测试通过 ≠ 系统可用：

- 前端单测过了、后端单测过了，串起来可能根本不通（契约差异、CORS、鉴权头）
- 结合 = 全链路（UI → API → DB → 响应 → 展示）真实运转
- Mock 不替换等于没有结合——真实接口连通是验收的硬条件

### 7. 可观察的集成

每个适配点都要能被验证：

- 适配完成的标准不是"看起来对了"，而是有契约测试/冒烟清单能证明
- 集成问题必须可复现：记录复现步骤与日志证据
- 一次适配一处，验证一处——不要一口气适配完再一起试

### 8. 小步集成

频繁、小批次合并，绝不攒 PR：

- 集成地狱的教训：多个 PR 单独通过、合在一起出错，且难以定位
- 一次合并 1-2 个配对 PR，合并后立即重测，再继续下一个
- 小步 = 出错时能定位、能回滚、不阻塞他人

### 9. 交接文化

文档是给未来的人和 agent 的交接物：

- README/ADR/契约定稿/CHANGELOG 是团队记忆，代码只能展示"是什么"
- 文档与代码同时交付——合 main 时文档缺失 = 交付不完整
- 写"为什么"（为什么这样适配、为什么契约这样定），不写"是什么"

### 10. 兼容性优先

只加不改不删，破坏性变更要有版本化与迁移路径：

- 后端改动响应结构、前端改字段名——都是破坏契约，都要走契约变更流程
- 向后兼容是契约的承诺：已发布的字段不删、不改语义
- 兼容性测试不是可选项——合 main 前的最后一道保险

### 11. 每行代码都是负债

适配代码也是代码：

- Mock 切换后，Mock 开关与假数据要清理（残留 Mock = 事故隐患）
- 一次性的 mapping 补丁要标注并尽快收敛进契约
- 适配层代码越少越好——理想状态是契约一致后适配层近乎透明

### 12. 能跑 → 对 → 快

```
先跑通全栈（能跑）→ 再对齐契约正确性（对）→ 最后才优化（快）
```

- 结合工作的第一优先级是让链路真实运转
- 顺序颠倒（先优化再对齐）会导致在错误的基础上优化

## vibe coding 协作原则（结合角色）

1. **结合 = 消除前端与后端的差异**，不是代替任何一方
2. **功能问题退回开发人员**，适配问题自己解决——边界由契约文档划定
3. **每个 PR 独立确认、独立合并、合并后立即重测**
4. **契约文档先于适配代码**——先比对契约，再写适配
5. **合 main 前所有门禁真实通过**——验收、兼容性、脱敏扫描缺一不可
6. **文档与代码同时交付**——README、契约定稿随功能一起进 develop

## AI 反模式（结合角色专属）

| 反模式 | 后果 |
|--------|------|
| "顺手把功能也改了" | 越界。开发人员的职责被抢，契约边界混乱 |
| "Mock 也能演示，先这样吧" | 假验收。真实接口不通的问题留到生产才发现 |
| "直接 push main" | 绕过流程。合 main 只提交 merge PR，人工 merge |
| "先合并，冲突再说" | 集成风险累积。合并前就要评估冲突面 |
| "契约文档后面再补" | 契约不同步 = 新的差异源。先对齐文档再改代码 |
| "适配代码留着以后删" | 残留适配层和 Mock 都是负债。交付时就要干净 |
