# 文档

## 概述

文档记录"为什么"而不是"是什么"。代码展示做了什么，文档解释为什么这样做、考虑过哪些方案、有什么约束。

## 角色边界（结合人员视角）

项目文档的归属：

| 文档 | 责任方 |
|------|--------|
| `README.md`、`docs/`（架构、启动、部署）、CHANGELOG、ADR | **本角色（结合人员）** |
| `docs/api-contracts/` | 契约定稿由本角色负责；初稿由后端开发人员在规格阶段产出 |
| `docs/frontend/` | 前端开发人员维护（本角色可审阅，不代写） |
| `docs/backend/` | 后端开发人员维护（本角色可审阅，不代写） |

- 本角色负责文档的**整合与定稿**：README、架构说明、启动/部署指南、契约最终版
- 开发人员的领域文档（docs/frontend、docs/backend）由他们自己写，本角色只在评审时指出缺失
- 文档模板（如 docs 技能内的 ADR/README/CHANGELOG 结构）供参考，不强制三方使用

## 流程

### 第 1 步 — 需求澄清
问清楚：
- 要写什么文档？（README / API / ADR / CHANGELOG / 开发指南）
- 读者是谁？（开发者 / 用户 / 贡献者 / AI agent）
- 有什么参考资料？（现有代码、已有文档草稿、参考项目）

### 第 2 步 — 规格与计划
- 确定文档结构和目录
- 列出需要覆盖的内容要点
- 如果有现有文档，标注哪些需要更新

### 第 3 步 — 权限门禁
question: "文档结构和内容大纲已写好。可以开始写了吗？"

### 第 4 步 — 编写

**ADR（架构决策记录）：**

技术决策应该记录在 `docs/adr/` 下：

```markdown
# ADR-001: [决策标题]

## 状态
已接受 / 被 ADR-XXX 取代 / 已废弃

## 日期
2026-07-30

## 背景
为什么要做这个决策？上下文和问题描述。

## 决策
选择了什么方案？

## 候选方案
方案 A: 优点 / 缺点 / 为什么没选
方案 B: 优点 / 缺点 / 为什么没选

## 影响
- 正面：...
- 负面：...
- 迁移成本：...
```

**ADR 生命周期：** 提议 → 接受 → (被取代 或 废弃)。旧的 ADR 不要删除，它们记录了历史背景。

**内联注释原则：**
- 注释"为什么"，不是"是什么"
- 好的：`// 这里用滑动窗口限流而不是固定窗口，防止突发流量在窗口边界打穿`
- 差的：`// 计数器加1`
- 不要留 TODO 不处理，不要留注释掉的代码

**README 结构：**
```markdown
# 项目名

一段话描述项目做什么。

## 快速开始
1. 克隆
2. 装依赖
3. 配置环境
4. 启动

## 命令
| 命令 | 说明 |

## 架构
项目结构和关键设计决策。链接到 ADR 详情。
```

**CHANGELOG：**
```markdown
## [1.2.0] - 2026-07-30
### 新增
- 功能描述 (#123)
### 修复
- Bug 描述 (#124)
### 变更
- 改动描述 (#125)
```

### 验收
- 通读全文检查准确性
- 检查格式（标题层级、链接、代码块）
- question 汇报完成，你审阅反馈

## 验证清单

- [ ] 文档内容与代码/事实一致
- [ ] 格式正确（标题层级、链接、代码块）
- [ ] 记录了"为什么"而非仅"是什么"
- [ ] 用户已审阅反馈

## 为 AI Agent 写文档

Agent 会读取项目文档来理解上下文。特别关注：
- **AGENTS.md / SKILL.md** — 项目约定和流程
- **ADR** — 技术决策的历史原因（防止 agent 重复做决策）
- **已知陷阱** — 防止 agent 踩坑

## 反合理化

| 借口 | 现实 |
|------|------|
| "代码自文档化" | 代码展示做了什么，不展示为什么、被否决的方案、约束条件 |
| "以后再写文档" | 以后永远不会写。写文档的最佳时机是现在 |
| "没人看文档" | Agent 会看。未来的你会看。3个月后的你也会感谢现在的你 |
| "注释会过时" | 注释"为什么"是稳定的；注释"是什么"才会过时 |
