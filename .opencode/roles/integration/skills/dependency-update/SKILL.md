# 全栈依赖升级（结合角色版）

## 概述

依赖升级影响面广：前端依赖影响 UI/构建，后端依赖影响 API/数据层，CI 工具链影响发布流程。本角色负责**跨全栈的依赖升级**——涉及前端 + 后端（+ CI 工具链）任一组合的升级在此处理，确保升级后整体兼容。

**思想（详见 `integration-philosophy`）**：兼容性优先（卡片 10）——升级不得破坏已发布的契约；每行代码都是负债（卡片 11）——升级任务的代码改动只做兼容性修复。

**单领域升级**（只动前端或只动后端）由对应开发人员在自己流程处理；本技能处理跨领域升级、**仅 CI 工具链升级**（actions 版本、runner、docker-compose、缓存配置等）与升级后的全栈验证。

## 步骤调整

### 第 1 步 — 需求澄清
询问：
- 升级什么？（具体包名，或"全部依赖"）
- 目标版本？（指定版本 / latest / 修复漏洞）
- 升级动机？（新功能、漏洞修复、性能、维护要求）
- 有无时间或范围约束？（不影响某功能、某客户端、数据库兼容）

### 第 2 步 — 规格与计划
- **审查 changelog / release notes**（GitHub Releases、CHANGELOG.md、包管理器页面）：
  - 破坏性变更（breaking changes）清单
  - 弃用 API（deprecations）——作为后续迁移清单
  - 与新版本相关的已知问题（GitHub issues）
- **影响面分析**：grep 代码库中该包的所有使用点（import、API 调用、配置项）：
  - 前端：构建配置、UI 行为、浏览器兼容
  - 后端：数据层（ORM/驱动）变更对 SQL/事务行为的影响
  - 交叉影响：后端响应结构变化是否破坏契约（`docs/api-contracts/`）？前端依赖的 API 行为是否变化？
- **升级策略**：
  - 相邻 major 逐个升（如 v2→v3→v4），跳过 major 升级风险高
  - 一次只升一个 major 范围，验证后再继续
  - 批量 minor/patch 可合并（低风险），但须记录全部变更
- **验证计划**：升级后跑什么（前端 + 后端测试套件、契约核对、构建、类型检查、lint、性能基线对比；**CI 工具链升级场景：workflow 文件语法校验（actionlint 或等效）**）
- **回滚方案**：记录当前锁定版本，升级失败可 `git revert` 或安装旧版本

### 第 3 步 — 权限门禁
呈现："升级 [包名] 从 [版本] 到 [版本]。破坏性变更：[摘要]。影响面：[N 个文件，前端 X / 后端 Y]。我可以继续吗？"

### 第 4 步 — 执行升级
- 用精确版本升级（**不用 `@latest`/`latest`**，锁定已验证的版本）
- 升级后立即检查：
  - 漏洞扫描结果（升级不应引入新的高危漏洞）
  - 依赖树完整性（peerDependencies/传递依赖冲突）
  - 锁文件已更新并提交（`package-lock.json`/`pnpm-lock.yaml`/`requirements.txt`/`pom.xml` 等必须入库）
- 逐 major 升级时，每步之间运行测试
- **编码修复**：升级导致的 breaking changes 在本技能内处理（改 API 调用、配置、类型），但遵守最小改动原则——升级任务里不夹带功能开发
- **契约保护**：升级涉及后端时，确认响应结构未被意外改变；涉及前端时，确认 API 调用方式兼容

### 第 5 步 — 验收
- 完整测试套件通过（前端 + 后端，含契约测试与错误路径）
- 构建 + 类型检查 + lint 通过（前端 + 后端）
- 数据层依赖升级：迁移/ORM 行为验证（数据读写正常）
- 手动冒烟：受影响功能正常
- 全栈连通抽查：升级跨前后端时，跑通一条核心链路（真实接口）
- **CI 工具链升级场景（必查）：推送后 CI 管道实际运行一次且全部通过**（workflow 语法、缓存、依赖安装）
- 记录：升级后的实际版本、处理过的破坏性变更

### 第 6 步 — 兼容性
- 门禁：`question` 请求许可
- 回归重点：所有依赖被升级包的功能（按第 2 步影响面清单逐项过）
- **性能基线对比**：关键接口延迟/吞吐量无回退
- 向后兼容确认：API 契约未变、既有客户端不受影响（如升级涉及浏览器兼容，检查目标浏览器）
- 全栈回归：按 `compatibility-test` 范围抽查（前端页面、后端 API、集成连通）
- 发现问题：汇总返回第 2 步

## 特殊场景

- **高危漏洞**：优先修复。无直接升级路径时记录缓解措施（配置规避、等待上游修复），不擅自换库
- **过旧 major（落后 2+ 个版本）**：先逐 major 升到中间版本再继续，禁止直接跳升
- **数据层依赖（ORM/驱动）**：升级前后对比迁移/事务/SQL 行为，数据完整性优先
- **升级导致测试失败**：判断是测试过时还是行为变更；行为变更需确认是否符合预期，禁止静默改测试掩过
- **前端/后端联动的破坏性变更**（如后端框架升级改变响应序列化）：按 `api-contract-integration` 核对清单重跑，契约差异按流程处理

## 常见借口

| 借口 | 现实 |
|------|------|
| "升到 latest 就行" | latest 可能有你还没准备好的 breaking changes。锁定验证过的版本 |
| "小版本升级不用看 changelog" | minor 也可能有行为变更（弃用、默认值变化）。至少扫一眼 release notes |
| "升级失败就回滚，不用提前计划" | 回滚前记录当前版本是计划的一部分，失败时才知道回到哪 |
| "顺手把相关代码也重构了" | 升级任务只做兼容性修复。重构另开任务 |
| "前后端各自升各自的，不用一起验证" | 跨领域升级必须全栈验证——单独通过、合起来出错的经典场景 |

## 验证清单

- [ ] changelog 已审查，breaking changes 已列出
- [ ] 影响面（所有使用点）已盘点，交叉影响（契约）已评估
- [ ] 升级用精确版本，锁文件已更新并提交
- [ ] 逐 major 升级且每步验证
- [ ] 漏洞扫描无新增高危漏洞
- [ ] 前端 + 后端测试/构建/类型/lint 全部通过（含契约测试）
- [ ] CI 工具链升级场景：管道实际运行一次全部通过
- [ ] 契约核对无新增差异（涉及后端升级时）
- [ ] 性能基线无回退，API 契约未变
- [ ] 受影响功能回归通过（第 6 步）
- [ ] 回滚方案已记录
