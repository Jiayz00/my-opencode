# 兼容性测试

## 概述

这是核心工作流的第 6 步。用户验收之后，验证改动不会破坏任何现有功能。这是在测试容器中进行的全栈、全覆盖回归测试。

## 服务器访问

本技能需要访问测试服务器。遵循 `vibe-core` 中的**敏感信息处理**规则：

1. 检查环境变量：`OPENCODE_TEST_HOST`、`OPENCODE_TEST_USER`、`OPENCODE_TEST_KEY`、`OPENCODE_TEST_PORT`、`OPENCODE_TEST_DIR`
2. 如果缺失，使用 `question` 一次向用户询问一个变量
3. 绝不将凭据保存到文件或回显

## 流程

### 1. 门禁
使用 `question` 工具向用户请求许可：
- "兼容性测试将运行全栈回归测试，以确保改动不会破坏任何现有功能。测试范围涵盖前端、后端、API、数据库和集成。我可以开始吗？"
- 未经明确许可不得开始

### 2. 测试准备
- 确保测试服务器环境干净（无验收测试遗留的过期状态）
- 部署带改动的版本：SSH → docker-compose up -d --build
- **部署失败**：检查容器日志 → 重试一次 → 仍失败则停止并报告，不进入回归阶段
- 如有需要，准备测试数据

### 3. 前端回归
- 验证所有现有页面/路由无错误加载
- 检查关键用户流程仍然可用
- 无新的控制台错误
- 响应式布局未被破坏

### 4. 后端回归
- 运行完整测试套件
- 验证所有现有 API 端点正确响应
- 检查向后兼容性（如果 API 契约有变更）
- 负载下无性能退化

### 5. 集成回归
- 前端-后端连通性仍然正常
- 数据库查询返回预期结果
- 认证/授权流程未改变
- 第三方集成仍然可用

### 6. 问题处理
- 如果发现问题：
  - 收集完整详情（日志、截图、复现步骤）
  - 汇总每个问题并标注严重程度
  - 返回核心工作流第 2 步
- 如果没有问题：向用户报告

### 7. 最终报告
使用 `question` 工具：
- "兼容性测试已完成。所有回归测试通过。[列出测试内容]。可以提交 develop → main 的 merge PR（人工 merge）。"

## 常见借口

| 借口 | 现实 |
|----------------|---------|
| "这个改动太小，不需要兼容性测试" | 小改动可能破坏大系统。运行测试。 |
| "我在第 5 步已经测过了" | 第 5 步测试的是新功能。第 6 步测试现有功能没有被破坏。范围不同。 |
| "测试容器搭建太费时间" | 这不是可选项。询问用户，让他们决定。 |

## 验证

- [ ] 用户已通过 `question` 授予许可
- [ ] 测试环境已清理（无验收测试遗留状态）
- [ ] 前端回归：所有页面/路由可加载、无新控制台错误、响应式未破坏
- [ ] 后端回归：所有测试通过、无性能退化
- [ ] 集成：前端-后端连通性完好
- [ ] 如发现问题，均已记录在案
- [ ] 最终报告已交付给用户
