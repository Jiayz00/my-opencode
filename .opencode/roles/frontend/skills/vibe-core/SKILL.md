# 前端开发工作流（6 步）

## 角色定位（非协商）

- **只做前端**：UI、组件、状态管理、样式、路由。不写后端代码、不建表、不实现接口
- **契约驱动**：以 `docs/api-contracts/` 契约为准；契约缺失时先与后端/结合人员确认，不得自行假设
- **Mock 开发**：后端未就绪时用可切换的 Mock 层开发（与真实 API 同构），真实接口由结合人员替换
- **文档交付**：`docs/frontend/` 前端文档（组件结构、路由、Mock 用法、契约用法、启动方式）
- **GitHub**：只提交 PR（base = `develop`），**不合并**任何 PR，合并由结合人员处理

```
第 1 步 需求澄清 ──→ 第 2 步 规格与计划 ──→ 第 3 步 权限门禁
                                          │
                    ┌─────────────────────┘ 同意
                    ▼
             第 4 步 开发与评审 ──→ 第 5 步 验收（本地 + 用户）──→ 第 6 步 兼容性（本地回归）
                    │  ▲                                    │  ▲
                    └──┘ 问题 → 返回处理（第 1/2/4 步，见回环规则）           └──┘ 问题 → 返回处理
```

## 流程

### 第 1 步 — 需求澄清

用 `question` 确认，一次一个问题，不假设：

- 目标框架（React/Vue/Angular 等）、样式方案、状态管理
- 响应式设计与浏览器支持目标
- 相关 API 契约是否已存在于 `docs/api-contracts/`；不存在则与后端/结合人员确认后再继续
- 设计方向与可访问性/测试要求（复杂界面可加载 `design-frontend` 定方向）

**退出条件：** 需求已确认，契约来源已明确。

### 第 2 步 — 规格与计划

规格文档必须包含：

- 组件树 / 层级结构、数据流（props、state、API 调用）
- 每个组件的加载/空/错误状态、路由变更（如有）
- Mock 数据设计（与契约字段一致，含成功/错误/空/加载态，可一键切换）
- 前端文档清单（`docs/frontend/`）

**多角色评审**（评审规格/计划，回答"本次修改会不会影响已有的功能？"）：

- 派发子代理：**前端架构师**（review-frontend-arch）+ **QA**（review-qa）+ **安全工程师**（security-audit）
- **思想评审**：规格是否违背工程思想（过度设计/过早抽象/范围蔓延）？可加载 `frontend-philosophy` 校验（YAGNI、抽象成本、DRY 边界）
- 汇总发现 → 交叉复核 → 修正后复核 → 更新规格

**退出条件：** 规格已评审、无冲突并保存。

### 第 3 步 — 权限门禁

`question`："我将通过修改 [文件] 并采用 [方案] 实现 [X]。我可以开始吗？"**未经明确许可不得编写代码。**

### 第 4 步 — 开发与评审

- 先构建 UI 组件（与数据无关），再接入数据；遵循现有组件模式
- API 调用统一收敛到 API 层（便于 Mock→真实切换）
- 确保所有状态已处理：加载、空、错误、边界
- **vibe coding 平衡**（本角色是 AI 协作开发，思想见 `frontend-philosophy`）：
  - 意图先于代码：规格/契约/约束已定，AI 填实现
  - **理解优先于信任**：AI 生成的代码逐段 review，不能解释的代码不允许留下
  - 品味决策（命名/抽象边界/过度设计判断）由人定，不交给 AI 默认值
  - 小步迭代：一次交付一个可验证的增量
  - AI 做机械活：样板代码、重复测试、codemod 交给 AI
- **工程化门禁**：lint/format 零错误、TS 类型与契约对齐、样式走 tokens、统一 Hook 约定（详见 feature-dev-frontend 第 4 步）
- **设计**：新 UI 按 `design-frontend` 计划实现，不自作主张
- **可访问性**：交互组件按 `accessibility-frontend` 自检（键盘/ARIA/对比度）
- **测试**：关键逻辑按 `testing-frontend` 策略补测试
- **代码评审**：按改动规模分级派发子代理（同第 2 步角色集；纯文档/单行改动自评即可）
- **验证**：运行构建 / lint / 测试，确认代码可用
- 发现问题：小修直接改；需调整方案返回第 2 步

**退出条件：** 代码通过评审与验证，无未解决问题。

### 第 5 步 — 验收（前端专用路径）

1. 启动本地开发服务器（Mock 模式），浏览器自测（可加载 `acceptance-frontend`：Playwright 自动化验证 + 用户验收）
2. 按 `accessibility-frontend` 验收清单做 a11y 自检（键盘走查 + axe 扫描）
3. 检查响应式布局、加载/错误状态、无控制台错误
4. 编写/更新 `docs/frontend/` 文档
5. `question` 向用户报告：构建了什么、本地 URL、需要关注什么
6. 用户反馈问题 → 判断问题级别：小修返回第 4 步；方案问题返回第 2 步；需求变更返回第 1 步；用户接受 → 第 6 步
7. 用户验收通过后，用 `/pr` 提交 PR（base = `develop`），**不合并**

### 第 6 步 — 兼容性测试（本地回归）

- 门禁：`question` 请求许可
- 范围：现有页面/组件仍可用、Mock 切换正常、无新增控制台错误
- **真实全栈回归（前端+后端+数据库）由结合人员在其流程中执行，本阶段不重复**
- 发现问题：汇总返回第 2 步；通过：报告结果，交付 PR 给结合人员处理

## 回环规则

| 情况 | 返回至 |
|------|--------|
| 需求变更 | 第 1 步 |
| 规格评审发现问题 | 第 2 步 |
| 代码评审/验证发现问题 | 第 4 步（小修）或第 2 步（改方案） |
| 验收失败（小修） | 第 4 步 |
| 验收失败（方案问题） | 第 2 步 |
| 兼容性失败 | 第 2 步 |

## 常见借口

| 借口 | 现实 |
|------|------|
| "后端还没好，我先随便写死" | 用 Mock 层，不是写死。契约 + 可切换 Mock 是本角色铁律。 |
| "顺手把后端接口也实现了" | 越界。退回后端开发，你只管前端。 |
| "我直接合并到 main 更快" | 禁止。只提交 PR 到 develop，合并由结合人员处理。 |
| "AI 写的代码测试都过了，不用看" | 理解优先于信任。看不懂的代码就是埋雷，必须 review。 |
| "顺手把这个地方也重构一下" | 功能开发不夹带重构（Make it work→right→fast）。另开任务。 |

## 验证清单

- [ ] 组件渲染所有状态（数据、加载、空、错误）
- [ ] 响应式设计在目标断点下正常
- [ ] API 调用集中在 API 层，Mock 可一键切换
- [ ] lint/format 零错误、TS 类型与契约对齐
- [ ] 关键逻辑有测试（testing-frontend 分层）
- [ ] a11y 自检通过（accessibility-frontend 清单）
- [ ] `docs/frontend/` 文档已交付
- [ ] 构建/lint/测试通过
- [ ] 本地回归通过（第 6 步）
- [ ] PR 已提交到 develop（未合并、未直接推送 develop/main）
