# 前端工程思想

## 概述

本技能是前端开发的"为什么"层——所有流程技能（feature-dev-frontend、testing-frontend 等）都从这里取思想。流程技能告诉你**做什么**，本技能告诉你**如何思考**。

沉淀自资深前端工程师的开发思想（收口、组件化、三重境界）与社区广泛实践（clean-code、抽象成本、Testing Library、Boring Technology、vibe coding 原意）。

## 三层境界

| 境界 | 表现 | 特征 |
|------|------|------|
| 会用 | 实现功能，能跑通 | 依赖框架 API，遇到问题查文档 |
| 用对 | 设计解决方案 | 组件拆分、状态设计、性能/可访问性主动考虑 |
| 用巧 | 权衡与品味 | 知道何时抽象、何时写重复代码、何时拒绝需求 |

**本角色要求：至少"用对"，关键决策（组件边界、状态分层、抽象取舍）要"用巧"。**

## 12 张思想卡片

### 1. 性能是功能（Perf is a feature）

- 主张：性能不是"优化项"，是产品功能的一部分。加载慢 = 功能不完整
- 反例：功能做完才想起性能，重要页面 5 秒才出内容却认为"功能没问题"
- 应用：Web Vitals 是**需求指标**不是优化建议（见 optimization-frontend）；每步开发考虑加载/渲染影响

### 2. 可访问性是基本人权

- 主张：键盘用户、屏幕阅读器用户、视觉障碍用户有权使用你的产品，不是"额外加分项"
- 反例："用户都用鼠标，a11y 以后再说"
- 应用：开发时按 accessibility-frontend 清单写，验收时逐项过

### 3. 每行代码都是负债

- 主张：代码的维护成本 > 编写成本。新增代码前先问：这一行值得永远被维护吗？
- 反例：为了"万一以后用到"提前写好大段未用代码
- 应用：删除死代码、不写"防御性将来码"（YAGNI）、评审时关注新增代码量

### 4. 抽象有成本（Abstraction has a cost）

- 主张（Goodbye Clean Code 教训）：抽象会隐藏重复，也隐藏理解成本与耦合。**被抽象隐藏的重复比显式重复更危险**——因为没人敢动那个"优雅"的抽象
- 反例：两处相似代码立刻抽公共层，三个月后无人能改那层代码
- 应用：**两处重复可接受，三处重复才抽象**；抽象必须让使用点显著更简单，否则不建

### 5. 收口思想（统一出口）

- 主张：所有同类操作走同一路径——API 请求统一收敛到 API 层、错误处理统一、出口统一。入口少、出口少，改动才有定点
- 反例：每个组件自己 fetch、自己 try/catch、自己写错误提示
- 应用：API 层、请求/错误处理封装、统一 Hook（见 feature-dev-frontend 第 4 步）

### 6. 组合优于继承

- 主张：组合（use 一个行为、渲染一个子组件）比继承（extends 一个基类）灵活、可预测
- 反例：为复用两行逻辑建"BaseComponent"继承链，改动基类全树遭殃
- 应用：组件复用用 props + 组合 + hooks；继承只用于框架明确要求的场景

### 7. Renderless 思想（行为与渲染分离）

- 主张：复杂行为（拖拽、弹窗逻辑、数据获取）可以做成"无渲染"组件/hook——只管逻辑与状态，渲染交给使用方
- 反例：把行为硬编码进一种视觉实现，换视觉必须重写逻辑
- 应用：行为可复用且视觉不固定时，用 renderless 模式

### 8. 渐进增强

- 主张：核心功能在最基础环境可用，增强（动画、高级交互）在支持时叠加；关键内容不被 JS 阻塞
- 反例：整个页面依赖 JS 渲染，脚本加载失败 = 白屏
- 应用：首屏关键内容尽早呈现；降级路径（加载失败、弱网）有兜底

### 9. Boring Technology（无聊技术原则）

- 主张：选成熟、可预期、社区活跃的技术，不为追新而承担风险。创新的机会成本应花在业务上
- 反例：为"新潮"引入未成熟库，遇到坑只能自己修
- 应用：新依赖引入前评估（维护活跃度、bug 记录、替代方案）；依赖升级不追 latest（见 dependency-update）

### 10. 约定优于配置

- 主张：项目内固定一套约定（目录结构、命名、组件模式、状态方案），减少"每处自行决策"的认知负担
- 反例：同一个项目同时出现三种列表渲染方式、两套状态方案
- 应用：遵循代码库既有模式，不另起炉灶；约定变化走评审并更新文档

### 11. DRY 有边界（重复 ≠ 复用）

- 主张：DRY 的目标是消除**会一起变化的重复**，不是消除所有相似代码。过早 DRY 会把本可独立演化的代码焊在一起
- 反例：两个未来走向不同的组件因"看起来像"被强行共用组件，改一处另一处跟着坏
- 应用：判断重复是否同源（同一业务规则）——同源才抽；不同源保持各自独立

### 12. Make it work, make it right, make it fast

- 主张（Kent Beck）：先让它能跑，再让它正确，最后让它快。顺序不可颠倒——不要边做边过度设计
- 反例：写功能的同时顺手"优化"和"抽象"，三件事互相污染，改到一半无法验证
- 应用：第 4 步先打通主路径（能跑）→ 补状态与边界（正确）→ 性能问题单独任务（快）；"顺便优化"是反模式

## vibe coding 协作原则（AI 时代的工程思想）

本流程是 vibe coding（AI 生成主要代码 + 人定义意图）的工程化版本。Karpathy 的原意是"信任迭代、用描述驱动"，但**vibe 不等于盲目**：

| 原则 | 内容 |
|------|------|
| 意图先于代码 | 规格、契约、约束、验收标准由人定义；AI 填实现。说不清需求就写代码 = 盲飞 |
| AI 写码，人定边界 | 架构决策、组件边界、状态分层、契约字段由人定；实现细节交给 AI |
| 理解优先于信任 | AI 生成的代码**必须 review**——"测试过了"不等于"理解过了"。改不理解的代码 = 埋雷 |
| 小步迭代，每步验证 | 一次交付一个可验证的增量；出问题能定位到具体一步 |
| AI 做机械活 | codemod、样板代码、重复测试、文档同步——让 AI 干它们擅长的 |
| 品味不可外包 | 命名、抽象取舍、设计方向、过度设计的判断是工程师的品味，不可交给 AI 默认值 |

**落地方式**：第 3 步权限门禁时说明"意图"（做什么/为什么/边界）；第 4 步对 AI 生成代码做 review（理解 + 品味审查）；评审子代理（review-frontend-arch）承担"品味审查"角色。

## AI 时代反模式（评审时重点扫）

| 反模式 | 表现 | 对策 |
|--------|------|------|
| 过度抽象 | AI 把两处相似代码抽象成通用层 | 用思想卡片 4：两处重复可接受 |
| 跳过理解直接复制 | 从别处复制不理解的行为 | review 时必须能解释每段代码在做什么 |
| 测试只求覆盖 | 大量 mock 内部细节的"假测试" | 用 testing-frontend：测行为不测实现 |
| 一次性代码不清理 | 原型代码混入生产、死代码残留 | 每行代码都是负债（卡片 3） |
| 防御性将来码 | "以后可能用到"的接口/配置 | YAGNI：只做需求要求的事 |
| 顺手优化 | 功能开发中夹带"顺便优化/重构" | 卡片 12：顺序不可颠倒 |

## 验证清单

- [ ] 关键决策（组件边界/状态分层/抽象取舍）达到"用对"以上水平
- [ ] 新抽象通过卡片 4 检验（三处重复 + 使用点显著更简单）
- [ ] 无"防御性将来码"、无死代码
- [ ] 重复代码判断过 DRY 边界（同源才抽）
- [ ] AI 生成的代码已 review（能解释、无过度抽象）
- [ ] 功能开发未夹带"顺便优化/重构"
