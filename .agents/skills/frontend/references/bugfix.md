
# 缺陷修复（前端）

## 概述

缺陷修复遵循 6 步工作流，但在第 2 步更强调复现和根因分析。目标是修复根本原因，而不仅仅是表象。

**思想（详见 `references/philosophy.md`）**：最小修复——只改缺陷相关代码，不夹带重构/优化/顺手修复其他问题；每行代码都是负债，修复引入的改动量应等于根因范围。

## 步骤调整

### 第 1 步 — 需求澄清
询问：
- 复现步骤（精确、详细）
- 预期行为与实际行为
- 环境详情（浏览器/操作系统/版本）
- 何时开始出现？近期是否有任何变更？
- 严重程度（阻塞 / 严重 / 轻微）

### 第 2 步 — 规格与计划
- 第 1 步：**复现** —— 确认你能看到该缺陷
- 第 2 步：**定位** —— 确定根本原因（具体文件、函数、条件）
- 第 3 步：**设计修复方案** —— 决定改什么以及为什么
- 对于复杂缺陷：编写一个描述根因和修复方案的精简规格
- **结合人员退回的缺陷**：先确认归属（前端错 / 契约错）；前端错自己修，契约错不自行改契约文档，退回结合人员定稿

### 第 3 步 — 权限门禁
呈现："我已确认根本原因是 [file:line] 中的 [X]。修复方案是 [方案]。我可以继续吗？"

### 第 4 步 — 开发
- 应用修复
- 添加能够捕获该缺陷的回归测试
- 验证修复生效且现有测试仍然通过

### 第 5 步 — 验收
- 确认缺陷已解决（执行复现步骤）
- 运行现有测试套件
- 进行视觉检查（浏览器中确认修复无视觉回退）

### 第 6 步 — 兼容性
- 门禁：向用户请求许可
- 运行聚焦于受影响区域的回归测试
- 发现问题：汇总并按角色主流程回到第 2 步

## 常见借口

| 借口 | 现实 |
|----------------|---------|
| "我知道哪里出错了，直接修就行" | 跳过复现可能会修错地方。先复现。 |
| "这是单行修复，不需要计划" | 单行修复也需要根因分析。 |
| "我以后再补回归测试" | 要么现在，要么没有。回归测试是修复的一部分。 |
| "顺手把旁边的代码也优化下" | 最小修复。夹带改动让回归面扩大，bug 修复只改根因。 |

## 验证

- [ ] 缺陷已复现并确认
- [ ] 已识别根本原因（而不仅仅是表象）
- [ ] 修复针对根本原因
- [ ] 已添加回归测试
- [ ] 所有现有测试通过
- [ ] 受影响区域回归通过（第 6 步）
