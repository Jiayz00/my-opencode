
# 安全审计

## 概述

只读安全审查。你分析代码中的漏洞并给出发现。**不得修改任何代码。**

**多角色评审中的角色：** 在 Step 2 规格评审 / Step 4 代码评审中，本参考资料 由安全工程师子代理加载，评审规格/计划或代码改动的安全性，回答"本次修改会不会引入安全风险"。代码评审模式下发现必须带 file:line 引用。

## 工作流调整

### 第 1 步 — 澄清
询问用户：
- 范围：审计什么（特定文件、模块，还是整个代码库）
- 威胁模型：风险画像是什么？（面向公众？处理敏感数据？PCI/HIPAA 等合规要求？）
- 是否有需要跟进的历史审计发现

### 第 2 步 — 分析（替代规格与计划）
从以下安全维度进行审查：
- **认证：** 会话管理、密码处理、MFA、令牌验证
- **授权：** 访问控制检查、权限提升路径
- **输入验证：** SQL 注入、XSS、命令注入、SSRF
- **数据保护：** 加密（静态和传输中）、密钥管理
- **依赖：** 已知漏洞版本、供应链风险
- **配置：** 默认凭据、调试端点、CORS、安全响应头

### 前端安全专项（必查，前端改动时逐项过）

**客户端密钥与存储**
- API key / token 是否泄漏进 bundle（`VITE_` 等前缀变量会被打包进前端产物，任何前端密钥都不可保密——须经服务端代理/网关，禁止把第三方密钥直放前端）
- 持久化会话优先使用服务端设置的 HttpOnly cookie；若架构采用短期 Bearer token，禁止持久化到可被 XSS 读取的存储，并审查生命周期、刷新与撤销策略
- Cookie 会话检查 Secure + HttpOnly + SameSite 和 CSRF 策略；服务端会话变更移交 backend/integration
- 源码/产物中硬编码凭据扫描（`-----BEGIN KEY-----`、`sk-`、`AKIA`、`ghp_` 等，见 git-workflow 脱敏表）

**XSS 与输出**
- 危险插值点审查：`dangerouslySetInnerHTML` / `v-html` / `innerHTML` 是否处理不可信内容
- 用户输入在 URL、属性、事件绑定处的编码
- CSP 是否配置（`Content-Security-Policy`），内联脚本/样式是否被允许

**传输与响应头**
- 混合内容：HTTPS 页面禁止读取 HTTP 资源
- 安全响应头：HSTS、X-Frame-Options（防点击劫持）、X-Content-Type-Options: nosniff、Referrer-Policy、Permissions-Policy
- 外链 `target="_blank"` 必须带 `rel="noopener noreferrer"`

**依赖与第三方**
- `npm audit` / 依赖漏洞扫描结果，高危漏洞是否未处理
- 第三方脚本（埋点、地图、SDK）的权限与数据流向审查
- iframe 嵌入场景是否配置 `sandbox` / `allow` 白名单

**错误处理**
- 生产环境不暴露堆栈、内部路径、框架内部信息（OWASP A09）
- 调试端点/console 调试输出在生产是否关闭

编写发现报告：
- 严重级别：严重 / 高 / 中 / 低 / 提示
- 位置：代码评审模式下必须为 file:line（规格评审用文档路径/章节）
- 影响：攻击者可以利用它做什么
- 修复：具体的修复步骤

### 第 3 步 — 只读报告
用户已请求审计时直接展示报告；只有修复、额外验证或其他有副作用操作需要另行许可。

### 第 4 步 — 不适用（只读）

### 第 5 步 — 展示发现，等待用户反馈。

### 第 6 步 — 不适用（只读，无兼容性回归）

## 规则

- 只读审查，不修改任何文件
- 不运行会修改系统的命令
- 报告内建议须自洽（与其他角色的冲突由主代理交叉复核裁决）
