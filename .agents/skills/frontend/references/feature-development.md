
# 功能开发 — 前端

## 概述

在构建新的面向用户的功能时使用本参考资料。通用 6 步流程仍然适用。本参考资料为每一步补充前端相关的细节。

## 角色边界

- **只做前端**：不写后端代码、不建表、不实现接口
- **契约驱动**：以 `docs/api-contracts/` 契约文档为准（初稿由后端开发在规格阶段产出）；契约缺失时先与后端/结合人员确认，不得自行假设
- **Mock 开发**：后端接口未就绪时，用可切换的 Mock 层开发（与真实 API 同构）；真实接口由结合人员统一替换
- **文档交付**：完成 `docs/frontend/` 前端文档
- **PR 目标**：提交 PR 到 `develop`（集成分支），不直接合并到 main

## 步骤调整

### 第 1 步 — 需求澄清
具体询问：
- 目标框架（React/Vue/Angular 等）
- 样式方案（CSS Modules/Tailwind/styled-components 等）
- 状态管理需求
- 响应式设计要求
- 浏览器支持目标
- 相关 API 契约是否已存在于 `docs/api-contracts/`
- 设计方向：有无设计稿/现有 tokens；复杂界面可读取 `references/design.md` 产出设计计划
- 可访问性要求：交互复杂度高时说明需按 `references/accessibility.md` 清单自检
- 测试要求：关键用户流程需配套测试（`references/testing.md` 策略）

### 第 2 步 — 规格与计划
规格必须包含：
- 组件树 / 层级结构
- 数据流（props、state、API 调用）
- 每个组件的加载/成功/空/错误状态，以及数据获取场景适用的 stale/partial 状态
- 路由变更（如有）
- Mock 数据设计（与契约字段一致，含加载/成功/空/错误及适用的 stale/partial 状态）
- **列出本功能实际使用的契约字段子集**（本步骤在对话中形成；Step 3 批准后写入 `docs/frontend/` 契约用法节）
- 前端文档清单（`docs/frontend/`：组件结构、路由、Mock 用法、契约用法、启动方式）

### 第 3 步 — 权限门禁
按角色主流程 Step 3 请求许可："我将通过修改 [文件] 并采用 [方案] 实现 [X]。我可以开始吗？" **未经明确许可不得编写代码。**

### 第 4 步 — 开发
- 先构建 UI 组件（与数据无关），再接入数据
- 遵循代码库中现有的组件模式
- 确保加载、成功、空、错误及适用的 stale/partial 和边界状态都已处理
- 可用时优先使用现有的设计系统组件
- API 调用统一收敛到 API 层（便于后续 Mock→真实接口切换），**不**在后端实现任何逻辑

**工程化门禁（提交前必须全过）：**
- **lint / format**：ESLint + Prettier 零错误（无警告新增），未通过禁止提交
- **TypeScript 严格类型**：与契约字段对齐的 interface 定义，禁止 `any` 逃避类型检查（确需放宽须注明理由）
- **样式一致性**：颜色/间距/字号走 design tokens 或项目样式约定，禁止硬编码临时值；遵循项目样式方案（CSS Modules/Tailwind/等），不混用多套方案
- **组件拆分原则**：单一职责、可复用、props 显式最小化；渲染逻辑与业务逻辑分离
- **统一约定**：表单处理、数据请求、权限控制按项目既有 Hook/工具函数封装，不另起炉灶
- **新组件**：按 `references/design.md` 设计计划实现；交互组件按 `references/accessibility.md` 自检键盘与 ARIA
- **测试**：按 `references/testing.md` 策略为关键逻辑补测试（组件/集成/E2E 按风险分层）

**工程思想（开发时的取舍依据，详见 `references/philosophy.md`）：**
- **YAGNI**：只做需求要求的事。AI 生成代码容易"顺手多建一层/多加个配置"——发现就删
- **抽象成本**：两处重复可接受，三处重复才抽象；抽象必须让使用点显著更简单（Goodbye Clean Code 教训）
- **收口思想**：API 请求、错误处理、出口统一收敛到单一路径，不在组件里各写各的 try/catch
- **能跑→对→快**：先打通主路径 → 补状态与边界 → 性能单独任务；不边写边"顺手优化"
- **每行代码都是负债**：不写"万一以后用到"的代码；删除无用的注释代码

### 第 5 步 — 验收
- 启动本地开发服务器并自测（Mock 模式下）
- 在浏览器中验证（不仅是单元测试）：可读取 `references/acceptance.md` 执行自动化验证 + 用户验收
- 按 `references/accessibility.md` 验收清单做 a11y 自检（键盘走查 + axe 扫描）
- 检查响应式布局
- 目视检查加载/错误状态
- 编写/更新 `docs/frontend/` 前端文档，按核心工作流呈现结果并等待明确接受；Git 交付留到 Step 6 之后

### 第 6 步 — 兼容性测试
- 门禁：按角色主流程 Step 6 向用户请求许可
- 单独开发阶段以本地回归为准：现有页面/组件仍可用、Mock 切换正常
- 真实全栈回归（前端+后端+数据库）由结合人员在其流程中执行，本阶段不重复
- 回归通过后读取 `references/git-workflow.md` 和 `references/workflows/pr-flow.md`，提交目标为 `develop` 的 PR

## 验证清单

- [ ] 组件渲染加载、成功、空、错误及适用的 stale/partial 状态
- [ ] 响应式设计在目标断点下正常工作
- [ ] 无控制台错误
- [ ] API 调用集中在 API 层，Mock 可一键切换
- [ ] lint / format 通过，无新增警告
- [ ] TS 类型与契约字段对齐，无 `any` 逃避
- [ ] 样式走 tokens/项目约定，无硬编码临时值
- [ ] 无过度设计（YAGNI：只做需求要求的事，无"将来码"）
- [ ] 关键逻辑有测试（按 `references/testing.md` 分层）
- [ ] 交互组件通过 `references/accessibility.md` 自检
- [ ] 前端文档已交付到 `docs/frontend/`
- [ ] 现有测试仍然通过
- [ ] 遵循现有组件模式
- [ ] PR 已提交到 `develop`（未直接合 main）
