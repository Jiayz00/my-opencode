
# UI 设计质量

## 概述

本参考资料保障 UI 的视觉质量与独特性。AI 生成的设计容易落入模板化套路（米白底+衬线大标题+陶土色点缀；近黑底+荧光绿点缀；报纸排版细线+零圆角）。本参考资料要求：**设计要服务于具体需求，而不是默认模板**。适用于：

- **第 1-2 步（澄清与规格）**：确定设计方向与 tokens
- **第 4 步（开发）**：按设计计划实现，不自作主张
- **`references/review-frontend-architecture.md`**：作为设计质量维度审查依据

**核心原则**：设计是功能的一部分。用户界面首先要理解起来容易、用起来顺畅；美观服务于理解。

## 两遍法（Process）

### 第一遍：设计计划（动手前）

先审查现有设计系统、品牌规范、组件库和 tokens。已有体系优先复用和最小扩展；只有项目缺少对应能力或用户明确要求新方向时，才产出新的紧凑 token 方案。设计计划覆盖：

1. **视觉 tokens**：列出复用或新增的颜色、字体、间距、圆角和语义用途；token 定义可包含字面值，组件中避免临时特例
2. **字体角色**：遵循现有品牌字体；只有需要且许可允许时增加字体角色或依赖
3. **布局概念**：按改动复杂度给出一句话方案；存在实质布局取舍时再比较 2-3 个方案
4. **识别特征**：产品或页面需要差异化时定义；运维、后台和既有产品界面可保持克制一致

### 第二遍：复核（构建前）

对照需求检查设计计划：
- 每个选择是否是为这个需求做的，还是换任何项目都会这么选？
- 是 → 修改该部分，说明改了什么、为什么
- 复核通过后才开始写代码，颜色/字体/间距全部从 token 系统推导，不临时造值

### 构建 + 自批评

- 按计划实现；CSS 选择器注意 specificity 冲突（避免 `.section` 与元素选择器互相覆盖 margin/padding）
- 构建中持续自批评：有识别特征时，其余部分保持克制；无此需求时忠实复用现有系统
- 空间允许时截图检查自己的作品（一张图胜过千行代码）

## 设计 tokens 与主题

- 颜色、间距、圆角、阴影、字体优先走现有 design tokens；新增 token 必须有复用价值，避免组件内临时字面值
- 间距用 8pt 网格体系（4/8/16/24/32/48）
- 深色模式：两套主题都从 tokens 推导，不单独造色
- 响应式：移动端优先布局，断点处不破坏排版意图

## 排版

- 字号比例清晰（如 12/14/16/20/24/32），行高与字号配套
- 展示字体克制使用（标题/数字），正文保持可读性
- 文本对比度达标（见 `references/accessibility.md`）

## 界面文案（写作即设计）

- **从用户侧写**：命名用用户认识和控制的东西（"通知管理"而非"Webhook 配置"）
- **动词开头**："保存更改"而非"提交"；同一动作全程同名（按钮写"发布"，提示也写"发布"）
- **失败与空状态是指引而非态度**：说明发生了什么、如何解决；错误不道歉、不模糊
- **空屏幕是行动邀请**：给出下一步动作，而非孤零零的"暂无数据"
- 具体优于聪明；一句人话优于炫技措辞

## 可访问性底线（不可妥协）

- 响应式到移动端且可用
- 键盘焦点可见
- 尊重 `prefers-reduced-motion`
- 对比度达标（WCAG AA）

## 常见借口

| 借口 | 现实 |
|------|------|
| "这是流行风格，用的人多" | 流行 ≠ 适合。为需求做选择，不为模板做选择 |
| "先写代码，样式后补" | 设计决策（tokens/布局）影响组件结构。先定方向再写代码 |
| "这个配色我临时觉得好看" | 颜色来自 token 系统，不进临时值。改 token，不改特例 |
| "文案差不多就行" | 文案是界面的一部分。错误的文案让用户困惑 |

## 验证清单

- [ ] 已审查现有 design system；设计计划按需求记录复用或新增的 tokens、字体、布局和识别特征
- [ ] 颜色/字体/间距全部来自 tokens，无硬编码
- [ ] 需要差异化时识别特征明确；否则与现有产品视觉语言一致
- [ ] 文案从用户视角写，动作动词开头、名称全程一致
- [ ] 空状态/错误状态有引导，不空摆
- [ ] 响应式、键盘焦点、reduced motion 达标
- [ ] 对比度满足 WCAG AA
