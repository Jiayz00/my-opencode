
# 缺陷修复（结合角色版）

## 概述

缺陷修复遵循 6 步工作流，但在第 2 步更强调复现和根因分析。目标是修复根本原因，而不仅仅是表象。

**思想（详见 `references/philosophy.md`）**：集成问题必须可复现（卡片 7）——收集日志与证据是修复的第一步。结合角色的缺陷往往藏在**集成边界**：前端与后端单独都对，合起来行为不对（契约层 bug）。

## 步骤调整

### 第 1 步 — 需求澄清
询问：
- 复现步骤（精确、详细）
- 预期行为与实际行为
- 问题发生在哪一层？（前端展示 / 后端逻辑 / **集成边界**——接口连通、字段映射、契约差异、CORS/代理）
- 环境详情（浏览器/操作系统/版本、前端与后端版本组合）
- 何时开始出现？近期是否有任何变更（新 PR 合并、依赖升级、配置变更）？
- 严重程度（阻塞 / 严重 / 轻微）

### 第 2 步 — 规格与计划
- 第 1 步：**复现** —— 确认你能看到该缺陷
- 第 2 步：**定位** —— 确定根本原因（具体文件、函数、条件；集成边界问题要确定归属：前端错/后端错/契约错）
- 第 3 步：**设计修复方案** —— 决定改什么以及为什么
- 对于复杂缺陷：编写一个描述根因和修复方案的精简规格
- 归属判定：功能逻辑问题 → 退回对应开发人员；契约/适配问题 → 本角色修复并同步契约文档

### 第 3 步 — 权限门禁
呈现："我已确认根本原因是 [file:line] 中的 [X]。修复方案是 [方案]。我可以继续吗？"

### 第 4 步 — 开发
- 应用修复（最小改动——不顺手重构、不夹带优化）
- 添加能够捕获该缺陷的回归测试
- 验证修复生效且现有测试仍然通过
- 契约层修复：同步更新 `docs/api-contracts/`（差异消除后文档必须定稿）

### 第 5 步 — 验收
- 确认缺陷已解决（执行复现步骤）
- 运行现有测试套件（前端 + 后端）
- 集成边界缺陷：跑通受影响的核心链路（真实接口）
- 视觉检查：缺陷涉及 UI 展示时确认界面表现符合预期
- 验收未过：小修返回第 4 步，方案问题返回第 2 步

### 第 6 步 — 兼容性
- 门禁：向用户请求许可
- 运行聚焦于受影响区域的回归测试
- 契约变更场景：核对其他消费方不受影响（`references/api-contract.md` 兼容性检查）
- 发现问题：汇总返回第 2 步

## 常见借口

| 借口 | 现实 |
|------|------|
| "我知道哪里出错了，直接修就行" | 跳过复现可能会修错地方。先复现。 |
| "这是单行修复，不需要计划" | 单行修复也需要根因分析。 |
| "我以后再补回归测试" | 要么现在，要么没有。回归测试是修复的一部分。 |
| "前端后端都对，这 bug 找不到人负责" | 集成边界的问题正是本角色的职责。定位归属后按流程处理。 |
| "顺手把旁边代码也优化了" | 最小改动。修复之外的结构问题另开任务。 |

## 验证

- [ ] 缺陷已复现并确认
- [ ] 已识别根本原因（而不仅仅是表象），集成边界问题已明确归属
- [ ] 修复针对根本原因
- [ ] 已添加回归测试
- [ ] 所有现有测试通过（前端 + 后端）
- [ ] 契约文档已同步（契约层修复时）
- [ ] 受影响功能回归通过（第 6 步）
