
# 重构（结合角色版）

## 概述

重构是指在**不改变可观察行为**的前提下重构现有代码。关键挑战是在改善结构的同时保持行为不变。前后都要高度重视测试覆盖率。

**方向感（思想，详见 `references/philosophy.md`）**：重构的目标是让代码**更简单**，不是**更抽象**。结合角色重构的对象多为适配层与集成代码——理想状态是契约一致后适配层**近乎透明**（卡片 4/11）。如果适配代码需要靠复杂抽象才能"理解"，重构方向是**拆解**而非**加固**。

## 步骤调整

### 第 1 步 — 需求澄清
问清楚：
- 需要重构哪些代码，为什么
- "更好"是什么样（更简单？可读性？可维护性？）
- 哪些行为绝不能变（关键路径、边界情况、**API 契约**——契约不变是本角色重构的底线）

### 第 2 步 — 规格与计划
- **开始之前：** 检查目标代码的测试覆盖率。覆盖率低 = 风险高。
- 计划必须包含：
  - 现状分析（哪里有问题）
  - 目标状态（"好"是什么样）
  - 重构步骤（小步、可验证的增量）
  - 安全网策略（测试、类型检查、lint）
- **契约确认**：重构涉及前端 API 层或适配层时，确认契约不变（`docs/api-contracts/` 为准）；涉及适配层时，确认每个 mapping/补丁的原因标注仍准确
- **范围确认**：重构只动结构，不夹带功能修复（功能问题走 bugfix 或退回开发人员）

### 第 3 步 — 权限门禁
呈现："重构 [代码范围]。目标：[更好是什么样]。安全网：[测试/类型/lint]。契约不变。我可以开始吗？"

### 第 4 步 — 开发
- 一次只做一处改动
- 每次改动后：验证行为未变（测试 + 构建）
- 绝不在同一次改动中既重构又加功能
- 优先使用机械化的、工具辅助的重构（重命名、提取等）
- 适配层重构：每处 mapping 保持行为逐字节一致，重构后契约核对清单重跑

### 第 5 步 — 验收
- 完整测试套件必须通过（前端 + 后端）
- 对受影响的区域进行手动冒烟测试
- 全栈连通性抽查：涉及前后端交界时跑通一条核心链路
- 验收未过：小修返回第 4 步，方案问题返回第 2 步

### 第 6 步 — 兼容性
- 门禁：向用户请求许可
- 回归重点：重构涉及的模块及其调用方（按第 2 步影响分析逐项过）
- 无行为变化确认：对比重构前后的关键路径输出（接口响应、数据副作用）
- 契约未变确认：`references/api-contract.md` 核对清单无新增差异
- 发现契约/数据行为变化：返回第 2 步

## 常见借口

| 借口 | 现实 |
|------|------|
| "我加功能的时候顺便重构" | 一个改动里有两件事。重构绝不能和功能开发混在一起。 |
| "测试够好了" | 如果不敢确定覆盖率足够，先补测试再重构。 |
| "只是改个名，不会出问题" | 重命名会破坏 import、类型和序列化。要验证。 |
| "越抽象越好" | 重构方向是更简单。抽象有维护成本，拆解过度抽象也是重构。 |
| "适配层重构不影响行为，不用跑契约核对" | 适配层重构最容易悄悄改变字段映射。契约核对必须重跑。 |

## 验证清单

- [ ] 重构前测试通过（建立基线）
- [ ] 重构后测试通过（行为保持）
- [ ] 除重构范围外无行为变化
- [ ] 按既定标准，代码可度量地更好了（更简单/更快/更干净）
- [ ] 受影响模块及调用方回归通过（第 6 步）
- [ ] API 契约与数据结构未变（契约核对清单无新增差异）
- [ ] 适配层 mapping 原因标注仍准确
