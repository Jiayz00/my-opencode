
# 安全审计

## 概述

只读安全审查。你分析代码中的漏洞并给出发现。**不得修改任何代码。**

**多角色评审中的角色：** 在 Step 2 规格评审 / Step 4 代码评审中，本参考资料 由安全工程师子代理加载，评审规格/计划或代码改动的安全性，回答"本次修改会不会引入安全风险"。代码评审模式下发现必须带 file:line 引用。

## 工作流调整

### 第 1 步 — 澄清
询问用户：
- 范围：审计什么（特定文件、模块，还是整个代码库）
- 威胁模型：风险画像是什么？（面向公众？处理敏感数据？PCI/HIPAA 等合规要求？）
- 是否有需要跟进的历史审计发现

### 第 2 步 — 分析（替代规格与计划）
从以下安全维度进行审查：
- **认证：** 会话管理、密码处理、MFA、令牌验证
- **授权：** 访问控制检查、权限提升路径
- **输入验证：** SQL 注入、XSS、命令注入、SSRF
- **数据保护：** 加密（静态和传输中）、密钥管理
- **依赖：** 已知漏洞版本、供应链风险
- **配置：** 默认凭据、调试端点、CORS、安全响应头

### 集成安全专项（必查，集成/适配改动时逐项过）

- **Mock 残留**：Mock 开关/假数据是否残留到生产构建？（搜索 mock/fake/stub 字样与假数据文件）
- **调试端点**：调试路由、Swagger/文档端点是否在生产暴露？
- **CORS 配置**：白名单是否过宽（`*` 或包含未知来源）？凭据（cookies/认证头）与 CORS 组合是否安全？
- **契约泄露**：契约文档/错误响应是否暴露内部结构（堆栈、SQL、内部路径、第三方凭据）？
- **Secrets 扫描**：适配代码/环境变量文件是否带入真实凭据？（按 git-workflow 脱敏表逐项扫）
- **代理与转发**：开发代理是否把敏感头（Authorization）泄露到非目标主机？反向代理路径是否暴露内部服务？
- **认证边界**：前后端鉴权是否一致——前端隐藏入口不等于后端保护（接口层鉴权缺失 = 数据泄露）？
- **依赖引入**：适配/升级引入的新依赖是否有已知漏洞、供应链风险？

编写发现报告：
- 严重级别：严重 / 高 / 中 / 低 / 提示
- 位置：代码评审模式下必须为 file:line（规格评审用文档路径/章节）
- 影响：攻击者可以利用它做什么
- 修复：具体的修复步骤

### 第 3 步 — 只读报告
用户已请求审计时直接展示报告；只有修复、额外验证或其他有副作用操作需要另行许可。

### 第 4 步 — 不适用（只读）

### 第 5 步 — 展示发现，等待用户反馈。

### 第 6 步 — 不适用（只读，无兼容性回归）

## 规则

- 只读审查，不修改任何文件
- 不运行会修改系统的命令
- 报告内建议须自洽（与其他角色的冲突由主代理交叉复核裁决）

## 验证清单

- [ ] 所有安全维度都已覆盖
- [ ] 集成/适配改动已逐项过"集成安全专项"清单
- [ ] 每个发现都包含严重级别、位置、影响和修复
- [ ] 代码评审模式下每个发现均带 file:line 引用
- [ ] 报告内建议已自洽检查
- [ ] 审计期间未修改任何代码
- [ ] 报告可执行（用户能根据发现采取行动）
