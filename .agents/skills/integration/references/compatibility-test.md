
# 兼容性测试

## 概述

这是核心工作流的第 6 步。用户验收之后，按已确认的影响面验证改动不会破坏现有功能。测试在隔离、可重复的非生产环境中进行。

## 服务器访问

需要远程测试服务器时，遵循 `references/workflows/role-flow.md` 的写入和环境操作门禁及 `references/acceptance-fullstack.md` 的环境安全规则。优先使用 SSH alias；凭据不得保存或回显。

若使用 `TEST_SERVER_*`，变量名可出现在模板中，但真实非占位值不得进入仓库或报告。

## 流程

### 1. 门禁
向用户明确请求许可：
- "兼容性测试将运行全栈回归测试，以确保改动不会破坏任何现有功能。测试范围涵盖前端、后端、API、数据库和集成。我可以开始吗？"
- 未经明确许可不得开始

### 2. 测试准备
- 从 Step 2 的影响分析生成可枚举回归矩阵：页面、API、数据、鉴权、错误、第三方和性能基线
- 为当前 commit 使用独立环境标识，记录镜像 digest、数据基线、确定性 seed、清理与恢复方式
- 部署带改动的版本并等待 health checks；失败时恢复上一个已知版本或清理环境后停止
- 每个矩阵项记录期望、实际、版本和证据；未覆盖项必须记录风险接受人

### 3. 前端回归
- 验证回归矩阵中的现有页面/路由无错误加载
- 检查关键用户流程仍然可用
- 无新的控制台错误
- 响应式布局未被破坏

### 4. 后端回归
- 运行完整测试套件
- 验证回归矩阵中的现有 API 端点、成功与错误响应
- 检查向后兼容性（如果 API 契约有变更）
- 负载下无性能退化

### 5. 集成回归
- 前端-后端连通性仍然正常
- 数据库查询返回预期结果
- 认证/授权流程未改变
- 第三方集成仍然可用

### 6. 问题处理
- 如果发现问题：
  - 收集完整详情（日志、截图、复现步骤）
  - 汇总每个问题并标注严重程度
  - 返回核心工作流第 2 步
- 如果没有问题：汇总测试执行证据

### 7. 最终报告
测试执行证据确认后，单独请求许可呈现最终验收结论：
- "兼容性测试已完成。所有回归测试通过。[列出测试内容]。可以提交 develop → main 的 merge PR（人工 merge）。"

### 8. 清理或移交环境
- 默认清理本次独立环境、volume 和测试数据
- 需要保留时记录负责人、到期时间、访问范围和清理方式

## 常见借口

| 借口 | 现实 |
|----------------|---------|
| "这个改动太小，不需要兼容性测试" | 小改动可能破坏大系统。运行测试。 |
| "我在第 5 步已经测过了" | 第 5 步测试的是新功能。第 6 步测试现有功能没有被破坏。范围不同。 |
| "测试容器搭建太费时间" | 这不是可选项。询问用户，让他们决定。 |

## 验证

- [ ] 用户已明确授予兼容性测试许可
- [ ] 测试环境已清理（无验收测试遗留状态）
- [ ] 前端回归：所有页面/路由可加载、无新控制台错误、响应式未破坏
- [ ] 后端回归：所有测试通过、无性能退化
- [ ] 集成：前端-后端连通性完好
- [ ] 如发现问题，均已记录在案
- [ ] 测试矩阵和证据完整，最终报告已在单独许可后交付
- [ ] 测试环境已清理，或已记录负责人和 TTL
