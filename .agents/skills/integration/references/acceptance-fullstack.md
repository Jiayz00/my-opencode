
# 全栈验收

## 概述

本参考资料处理核心工作流第 5 步中的全栈验收路径。测试必须在可重复、与生产隔离的环境中进行，覆盖完整的前端-后端-数据链路。环境可以是本地容器、远程测试服务器或托管预览环境。

## 服务器访问

需要远程测试服务器时，遵循 `references/workflows/role-flow.md` 的写入和环境操作门禁：

1. 优先使用预配置 SSH alias；否则检查 `TEST_SERVER_HOST`、`TEST_SERVER_USER`、`TEST_SERVER_KEY`、`TEST_SERVER_PORT`、`TEST_SERVER_DIR`
2. 缺失时一次询问一个变量；不在对话中回显值
3. 验证目标明确标识为非生产环境、SSH host fingerprint 和允许的部署目录
4. 使用最小权限账户和隔离容器；PR 构建阶段不得挂载部署或生产凭据

## 流程

### 1. 预检查
- 所有单元/集成测试通过
- 构建成功（前端 + 后端）
- 选定的测试环境可访问，版本/commit、服务基线和清理方式已记录

### 2. 准备隔离测试环境
- 为当前 commit/PR 使用独立环境标识（例如独立 compose project、namespace 或 preview deployment）
- 记录镜像 digest、数据库基线、确定性 seed 和上一个可恢复版本
- 使用运行时和平台适配的部署方式；远程 SSH 只是可选实现，不得假设固定 shell 语法
- 等待 readiness/health checks 通过，再检查服务日志
- **部署失败**：保留证据，恢复上一个已知版本或清理当前隔离环境，然后停止，不进入验证阶段

### 3. 端到端验证
按验收矩阵走完完整流程：
- 前端连接后端
- API 端点正确响应
- 数据端到端流转（UI → API → DB 并返回）
- 错误传播正常（后端错误 → 前端展示）
- 覆盖未登录、无权限、校验失败、空数据、重复提交、网络超时和持久化失败等适用场景
- 每项记录 commit、环境、测试数据、期望结果、实际结果及日志/截图/请求响应证据

如果发现问题：
- 局部问题：记录证据并返回核心工作流 Step 4；重新说明文件和方案并取得写入许可后修复
- 方案问题：汇总完整信息并附日志/证据，返回核心工作流第 2 步
- 不得进入用户报告阶段

### 4. 用户报告
向用户呈现测试执行证据，并在提交最终验收结论前取得单独许可。报告包含：
- 实现摘要
- 测试环境 URL
- 需要验证的具体流程/功能
- 测试账户标识和安全获取渠道；不得输出密码、token、私钥或重置链接

### 5. 用户验收
- 等待用户确认验收
- 如果用户反馈问题或要求更改 → 判断级别：局部修复返回第 4 步；方案问题返回第 2 步；需求变更返回第 1 步
- 如果用户接受 → 进入第 6 步

### 6. 清理或移交环境
- 默认在验收结束后清理 preview/compose project、临时 volume 和测试数据
- 需要保留时记录负责人、用途、到期时间、访问范围和清理方式；不得无限期保留凭据或敏感测试数据

## 验证

- [ ] 应用已部署到隔离、可重复的非生产环境
- [ ] 前端 Mock 已关闭，真实接口连通
- [ ] 前端-后端连通性已验证
- [ ] 端到端流程正常（UI → API → DB）
- [ ] 错误处理端到端正常
- [ ] 测试证据已报告，最终验收结论已单独获准呈现
- [ ] 用户已接受
- [ ] 测试环境已清理，或已记录负责人和 TTL
