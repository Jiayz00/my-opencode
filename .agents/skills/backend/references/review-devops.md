
# DevOps 审查

## 概述

以 **DevOps 工程师**视角进行只读审查。用于 Step 2 规格评审（评审规格/计划）或 Step 4 代码评审（评审基础设施/部署改动）。核心目标：**确认本次修改不会破坏已有部署和环境**。

**不得修改任何代码。**

## 输入模式

- **规格评审模式**：评审规格/计划文档，输入 = 文档路径
- **代码评审模式**：评审代码改动 diff，输入 = diff 范围 + 相关文件路径 + 规格文档路径（如有）；发现必须带 file:line 引用

## 审查维度

### 基础设施即代码（IaC）
- 环境定义（服务器、数据库、中间件）是否以代码/配置管理，而非手工操作？
- 是否可重复搭建？新环境能否从零快速创建？
- 配置变更（config 文件、环境变量）是否导致现有实例不兼容？

### CI/CD 管道
- 构建流程（构建命令、构建产物）是否受影响？
- CI 管道（workflow 文件、触发条件、步骤）改动是否影响现有流程？
- 缓存、依赖安装是否可能失效？
- 管道是否内置安全门禁：SAST 静态扫描、SCA 依赖漏洞扫描、密钥扫描、SBOM 生成？

### 部署策略（必查）
- 是否有渐进式发布机制（feature flags / blue-green / canary）还是全量一次性切换？
- 是否支持零停机部署？
- 数据库迁移与部署顺序是否冲突？（先迁移后发布/先发布后迁移的策略是否明确）

### 回滚（必查）
- 回滚方案是否完备？回滚是否快速可执行（一键级）？
- 回滚后数据/配置是否一致？
- 是否有回滚演练？

### 安全与凭据
- 密钥是否集中管理（secrets 管理），而非硬编码在代码/配置文件？
- 访问控制是否遵循最小权限？（CI 账号、部署账号、RBAC）
- 新配置是否引入敏感信息暴露风险（日志、CI 输出、制品）？
- CI 日志是否脱敏？

### 监控与运维
- 日志是否集中收集？指标、告警是否覆盖新部署？
- 是否有告警响应流程（on-call 机制）？
- 是否引入新的运维负担（手动步骤、定时任务）？

### 审批与治理
- 高风险变更（生产环境、数据迁移、权限变更）是否有审批环节？
- 发布是否可审计（谁、何时、部署了什么版本）？

## 审查流程

1. 确认输入模式（规格评审 / 代码评审）
2. 读取规格/计划文档（或代码改动 diff 及相关文件）
3. 按上述维度逐一分析
4. 识别对已有环境/部署的影响点
5. 输出审查报告

## 输出格式

```markdown
# DevOps 审查报告

## 发现摘要
- 严重: X 项 / 重要: Y 项 / 次要: Z 项

## 发现列表
1. **[严重/重要/次要] 问题描述**
   - 位置: 配置或流程（代码评审模式必须为 file:line）
   - 影响: 影响哪些已有部署/环境
   - 建议: 修复方案
```

## 规则

- 只读审查，不修改任何文件
- 不运行会修改系统的命令
- 影响评估不可跳过——即使改动很小
- 每项发现必须说明对**已有环境**的影响
- 报告内建议须自洽（与其他角色的冲突由主代理交叉复核裁决）

## 验证

- [ ] 部署策略、回滚方案已评估
- [ ] 所有审查维度已覆盖
- [ ] 每个发现都有位置、影响、建议
- [ ] 代码评审模式下每个发现均带 file:line 引用
- [ ] 报告内建议已自洽检查
- [ ] 已确认对已有部署/环境无破坏性影响
- [ ] 审查期间未修改任何文件
