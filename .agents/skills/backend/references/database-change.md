
# 数据库变更

## 概述

数据库变更风险很高，因为它影响技术栈的所有层级。该工作流强调谨慎的迁移设计、数据保护和回滚规划。

**思想（详见 `references/philosophy.md`）**：数据一致性优先（卡片 5）——迁移要么完整要么可回滚，不能有"半迁移"状态；最小变更（卡片 10）——迁移任务不夹带重构。

## 步骤调整

### 第 1 步 — 需求澄清
询问：
- 需要存储/变更哪些数据
- 这是增量变更（新表/新列）还是破坏性变更（删除/重命名）
- 现有数据量（需要迁移多少数据？）
- 停机容忍度
- 回滚要求

### 第 2 步 — 规格与计划
规格必须包含：
- 模式变更（精确 SQL 或 ORM 迁移）
- 数据迁移策略（如果涉及移动/转换数据）
- 回滚迁移（如何撤销）
- 影响分析（哪些应用代码需要更新）
- 锁影响、事务日志/复制延迟、预计时长和观察指标
- 大表 backfill 的批次、限速、断点续跑和校验策略
- expand-migrate-contract 部署顺序；需要并存时明确双读/双写和清理阶段
- 备份/PITR 可用性、forward-fix 与回滚各自的触发条件

### 第 3 步 — 权限门禁
向用户明确确认呈现完整的迁移计划。用户必须在任何模式变更之前明确批准。

### 第 4 步 — 开发
- 可逆迁移先编写并验证回滚脚本；不可逆迁移必须先批准 forward-fix、补偿或 PITR 恢复方案，不得编写会丢数据的伪回滚
- 数据库凭据用环境变量（`.env`，不入库），不硬编码连接串
- 优先使用合成或匿名化数据；生产数据副本需要单独批准、最小权限、加密、访问审计和销毁期限
- 在代表性数据量上验证锁、时长、日志增长、复制延迟、批次恢复和新旧应用版本并存
- 验证迁移前后的数据完整性
- 生产迁移与回滚分别取得明确批准；不得把“验收未通过”视为执行回滚的授权

### 第 5 步 — 验收
向用户报告迁移结果、数据完整性、锁/性能证据、已知限制和恢复选项，等待明确验收。验收失败时先停止后续写入并评估 forward-fix、补偿或回滚；任何回滚都需单独说明数据损失风险、备份/PITR 状态并取得批准。

### 第 6 步 — 兼容性
- 门禁：向用户请求许可
- 对破坏性变更至关重要：
- 验证应用在新模式下正常工作
- 在隔离环境验证回滚、补偿或 PITR 恢复路径；不可逆迁移必须明确标记
- 使用真实数据量测试（迁移性能）
- 发现问题：汇总返回第 2 步

## 常见借口

| 借口 | 现实 |
|----------------|---------|
| "只是加一列而已" | 经典遗言。把回滚写上。 |
| "迁移是可逆的" | 证明它。测试回滚。 |
| "数据量小，不用测" | 模式变更会影响查询。用真实数据测试。 |

## 验证

- [ ] 迁移脚本干净运行
- [ ] 可逆迁移的回滚脚本已测试，或不可逆迁移的已批准恢复方案已验证
- [ ] 迁移前后的数据完整性已验证
- [ ] 应用代码已更新以匹配新模式
- [ ] 迁移已用真实数据量测试
