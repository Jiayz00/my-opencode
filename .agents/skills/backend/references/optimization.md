
# 后端优化

## 概述

后端优化遵循 6 步工作流。主要区别：第 2 步进行基线测量，第 4 步分阶段上线，第 5 步在测试容器中验证。

**定位（思想）**：性能是功能，不是优化项（详见 `references/philosophy.md` 卡片 8）。延迟与吞吐量是**需求指标**——p95 延迟超阈值意味着功能不达标，和"接口报错"是同等级的功能缺陷。未经测量，绝不优化。

## 量化指标（目标口径）

| 指标 | 含义 | 参考良好值 |
|------|------|-----------|
| p95 延迟 | 95% 请求的响应时间 | 核心读接口 < 200ms，写接口 < 500ms（按业务调整） |
| 吞吐量 | 每秒请求数（rps） | 按业务规模定基线，对比负载测试结果 |
| 错误率 | 5xx 占比 | < 0.1% |
| 内存 | 常驻内存/GC 频率 | 无持续增长（无泄漏）、GC 停顿可控 |
| 数据库 | 慢查询数、连接池使用率 | 无全表扫描、连接池不饱和 |

- 测量工具：autocannon/k6/artillery（负载）、Node Clinic/Profiling（CPU/内存）、数据库慢查询日志、APM（如接入）
- 基线必须记录：场景、负载参数、环境（测试容器一致口径），优化前后对比同一场景

## 步骤调整

### 第 1 步 — 需求澄清
问清楚：
- 哪个指标最重要？（延迟？吞吐量？内存？成本？）
- 当前性能和目标（量化：p95 从 Xms 降到 Yms）
- 负载模式（并发用户数、请求分布）
- 任何约束条件（不得更改 API 契约、不得影响数据一致性）

### 第 2 步 — 规格与计划
- 基线：在真实负载下对当前系统进行性能分析（记录场景/参数/环境）
- 计划必须包含带具体数字的优化目标（对照上表口径）

### 第 3 步 — 权限门禁
向用户明确确认请求许可："基线为 [指标: X]。目标为 [指标: Y]。方案：[Z]。我可以开始吗？"**未经明确许可不得编写代码。**

### 第 4 步 — 开发
- 一次只改一个组件
- 进入下一个优化前先做性能分析
- 每次更改都要有安全的回滚策略
- 回退未能改善指标的优化；即使失败的尝试也要记录发现

### 第 5 步 — 验收
- 在测试容器中、真实负载下进行测试（场景与基线一致）——测试容器 = 本地 Docker（Testcontainers/docker compose 等），本角色无远程环境访问；远程服务器或生产环境压测不在范围内，需转结合人员执行
- 验证 API 契约未变
- 在用户报告中呈现前后对比指标
- 指标未达标 → 返回第 4 步；方案问题 → 返回第 2 步

### 第 6 步 — 兼容性
- 门禁：向用户请求许可
- 验证优化未破坏已有 API、数据流与集成；性能基线无回退（其他接口对比）
- 发现问题：汇总并返回第 2 步

## 常见借口

| 借口 | 现实 |
|------|------|
| "这个优化显然更快" | 明显不是证据。测量前后对比。 |
| "我一次性优化所有东西" | 一次只改一处，否则你不知道哪个有效。 |
| "我的环境里指标看起来不错" | 测试容器 + 基线场景才是可比口径。 |
| "先把功能上线，性能以后再说" | 性能是需求指标。上线后返工成本更高。 |

## 验证清单

- [ ] 已采集基线指标（场景/参数/环境已记录）
- [ ] 每项优化都已独立验证
- [ ] API 契约未变
- [ ] 其他领域无性能回退
- [ ] 测试容器验证通过（与基线同场景对比）
