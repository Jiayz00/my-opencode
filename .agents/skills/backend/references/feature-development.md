
# 功能开发 — 后端

## 概述

在构建新的服务端功能时使用本参考资料。通用 6 步流程仍然适用。本参考资料为每一步补充后端相关的细节。

## 角色边界

- **只做后端**：API、数据库、业务逻辑、校验、认证；不写前端代码
- **契约产出**：规格阶段在对话中形成 API 契约初稿；Step 3 批准后写入 `docs/api-contracts/`（初稿字段/结构即契约基线，前端按此 Mock；定稿权归 integration）；契约变更须同步更新
- **文档交付**：完成 `docs/backend/` 后端文档
- **PR 目标**：提交 PR 到 `develop`（集成分支），不直接合并到 main

## 步骤调整

### 第 1 步 — 需求澄清
具体询问：
- API 风格（REST/GraphQL/gRPC 等）
- 需要的数据模型变更
- 认证/授权需求
- 性能需求（预期吞吐量、延迟）
- 需要遵循的现有模式
- 前端对该功能的调用场景（影响契约设计）

### 第 2 步 — 规格与计划
规格必须包含：
- API 端点（方法、路径、请求/响应结构）
- 数据模型 / schema 变更
- 业务逻辑流程
- 错误处理策略（错误码、错误消息格式）
- 校验规则
- **API 契约初稿**（本步骤在对话中形成；Step 3 批准后写入 `docs/api-contracts/`，定稿权归 integration）
- 后端文档清单（`docs/backend/`：API 端点、请求/响应示例、错误码、数据库 schema、环境配置）

### 第 3 步 — 权限门禁
按角色主流程 Step 3 请求许可："我将通过修改 [文件] 并采用 [方案] 实现 [X]。我可以开始吗？" **未经明确许可不得编写代码。**

### 第 4 步 — 开发
- 契约优先：先定义 API 结构（同步 `docs/api-contracts/`），再实现；端点/错误结构/分页/幂等按 `references/api-design.md` 规范
- 添加错误处理和输入校验（集中式错误路径，不各路由手写）
- 实现的同时编写测试（按 `references/testing.md` 策略分层：单元/集成/契约/错误流）
- 遵循现有的错误处理模式

**工程化门禁（提交前必须全过）：**
- **lint / format**：零错误（无警告新增），未通过禁止提交
- **类型检查**：严格类型，禁止 `any` 逃避（确需放宽须注明理由）
- **契约一致**：实现与 `docs/api-contracts/` 一致（schema 校验或契约测试通过）
- **错误处理**：统一错误结构（error 包裹层：code/message/details/requestId，见 `references/api-design.md`），无实现细节泄露（堆栈/SQL/内部路径）
- **幂等检查**：写操作是否需幂等设计（Idempotency-Key/唯一约束）——未设计须说明理由
- **数据层**：schema 变更遵守 `references/database-change.md` 流程（回滚脚本先行），索引覆盖关键查询
- **依赖**：新增依赖的必要性与成熟度评估（Boring Technology，见 `references/philosophy.md` 卡片 9）

**工程思想（开发时的取舍依据，详见 `references/philosophy.md`）：**
- **契约先行**：契约是前端 Mock 的依据，契约基线定稿权归结合人员（以消费者需求为准），实现中不自作主张改结构
- **收口思想**：错误处理、日志、出口统一收敛到单一路径，不在各路由各写各的 try/catch
- **幂等与重试**：写操作默认考虑幂等；重试安全是设计决策不是补丁
- **能跑→对→快**：先打通主路径 → 补错误处理与边界 → 性能单独任务；不边写边"顺手优化"
- **每行代码都是负债**：不写"万一以后用到"的代码；删除无用的注释代码

### 第 5 步 — 验收
- 运行完整测试套件（含契约测试与错误路径，按 `references/testing.md` 策略）
- 验证 API 响应与规格/契约一致
- 检查错误场景返回正确的状态码
- 验证认证/授权正常工作
- 编写/更新 `docs/backend/` 后端文档
- 验收未过：小修 → 返回第 4 步修复；方案问题 → 返回第 2 步调整规格；需求变更 → 返回第 1 步澄清
- 验收通过 → 按核心工作流呈现结果并等待明确接受；Git 交付留到 Step 6 之后

### 第 6 步 — 兼容性测试
- 门禁：按角色主流程 Step 6 向用户请求许可
- 后端独立回归：现有 API/路由仍可用、数据无损坏、契约向后兼容（只加不改不删）
- 前端联调与全栈回归由结合人员在其流程中执行，本阶段不重复
- 回归通过后读取 `references/git-workflow.md` 和 `references/workflows/pr-flow.md`，提交目标为 `develop` 的 PR

## 验证清单

- [ ] 所有端点返回正确的状态码
- [ ] 输入校验能拦截非法数据
- [ ] 在预期的位置强制实施认证/授权
- [ ] 错误响应与现有模式一致
- [ ] API 契约已更新到 `docs/api-contracts/`
- [ ] 后端文档已交付到 `docs/backend/`
- [ ] 所有测试通过
- [ ] 现有行为未被破坏
- [ ] PR 已提交到 `develop`（未直接合 main）
